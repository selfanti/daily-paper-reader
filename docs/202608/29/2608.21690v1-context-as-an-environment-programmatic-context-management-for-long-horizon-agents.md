## 摘要
LLM智能体越来越多地承担长时间运行的任务，其历史记录的增长远超单个模型上下文窗口的容量。现有方法将早期的交互压缩或提取选定信息到固定的记忆表示中，在未知未来需求之前就决定保留哪些内容。我们提出了Scroll，一种上下文管理器，将每个智能体会话视为一个可执行的会话环境。该环境由一个仅追加的事件日志和一个沙箱化的持久Python内核支撑。内核在模型调用之间维持一个类型化命名空间，允许工具输出、检索到的历史和派生状态被绑定到变量，而不是在每次调用时序列化到提示中。模型编写的代码通过exec搜索、实体化并转换会话状态；只有显式打印的投影才进入模型下一次调用的工作视图。因此，上下文管理成为一种编程任务，继承了LLM不断改进的编码能力，而事件日志保留了无损的历史事实。当工作视图接近其预算时，过时的片段被逐出但仍可恢复：驱逐索引维护着与事件日志精确地址相关联的紧凑地标，使得智能体可以直接导航到被逐出的区域，而不是搜索整个日志。以Qwen3.8-Max为主干，Scroll在LongMemEval_S上达到94.8%；在BEAM_10M上达到73.1%，超过最佳已发布记忆系统5.1个百分点；在LOCA_256K上达到86.7%，超过最佳已发布长时程智能体37.4个百分点。

## Abstract
LLM agents increasingly take on long-running tasks whose history grows far beyond a single model context window. Existing approaches compress earlier interactions or extract selected information into fixed memory representations, committing to what to preserve before future needs are known. We present Scroll, a context manager that treats each agent session as an executable Session Environment. The environment is backed by an append-only Event Log and a sandboxed, persistent Python kernel. The kernel maintains a typed namespace across model calls, allowing tool outputs, retrieved history, and derived state to be bound to variables rather than serialized into the prompt at each call. Model-written code searches, materializes, and transforms session state through exec; only explicitly printed projections enter the model's working view for the next call. Context management thus becomes a programming task that inherits the improving coding abilities of LLMs, while the Event Log preserves lossless historical ground truth. As the working view approaches its budget, stale spans are evicted but remain recoverable: an eviction index keeps compact landmarks tied to exact Event Log addresses, so that the agent navigates directly to evicted regions instead of searching the full log. With Qwen3.8-Max as the backbone, Scroll achieves 94.8% on LongMemEval_S; 73.1% on BEAM_10M, surpassing the best published memory system by 5.1 points; and 86.7% on LOCA_256K, exceeding the best published long-horizon agent by 37.4 points.

# 论文详细总结

## 1. 核心问题与整体含义（研究动机与背景）

- **核心问题**：LLM智能体在执行长时任务（如仓库级软件工程、开放网络深度研究）时，会话历史与工具输出会持续累积，远超单次模型调用的上下文窗口上限；且模型在长输入上的检索与推理能力会随长度显著退化。
- **现有方法的根本缺陷**：
  - **压缩方法**（截断、摘要、折叠工具输出）：在观察时对历史做有损变换，任何被省略的细节在未来都不可恢复。
  - **外部记忆系统**（事实提取、摘要、知识图谱）：在摄取时抽取固定表示，先于未来需求决定“什么值得保留”和“如何检索”。
  - 两者的共同问题是：**信息保留决策过早**，且原始日志即使存在于磁盘也无法被模型直接访问。
- **论文含义**：将上下文管理从“在提示词内管理序列化文本”转变为“在持久化可执行环境中进行程序化访问”。历史被保留在模型上下文之外，模型通过编写代码自主决定如何检索、计算和暴露信息，从而让上下文管理成为一种编程任务，并继承LLM编码能力的持续进步。

## 2. 方法论：Scroll 的设计

### 2.1 核心思想
- 把每次智能体会话建模为一个**可执行的 Session Environment**，由三层组件构成：
  - **仅追加事件日志（Event Log）**：记录所有交互事件（用户消息、模型回复、工具调用及结果），每条事件有不可变、单调递增的 `seq` 地址；实现基于 SQLite，支持 BM25 全文检索。
  - **持久化存储（Payload Store）**：大型工具输出或生成物被外部化到文件系统（JSON/artifact），日志中仅保留预览与恢复指针，通过惰性句柄访问。
  - **持久 Python 内核（Resident Namespace）**：跨模型调用保持变量，工具输出、检索结果、派生计算均可绑定为类型化变量；同时为每个变量维护名称、类型、大小、来源等元数据。
- **用户界面**（模型可用的四个操作）：
  | 操作 | 接口 | 作用 |
  |---|---|---|
  | 定位 LOCATE | `ms.search(query, k, ...)` | BM25全文检索+结构化过滤，返回带 `seq` 地址的候选 |
  | 实体化 MATERIALIZE | `ms.expand(seq)` / `ms.expand(lo, hi)` | 恢复精确记录或连续区间，并加载惰性句柄指向的paylaod |
  | 计算 COMPUTE | 普通 Python + 数据库/文件/工具接口 | 过滤、连接、聚合、解决更新、构建派生状态 |
  | 暴露 EXPOSE | `print(value)` | 将选定投影作为有界观察返回，其余状态留在内核 |
- **工作视图（Working View）**：仅由模型显式 `print` 的内容构成，系统提示词 + 工具定义 + 命名空间摘要作为固定前缀；返回的观察被追加到下一次模型调用上下文。

### 2.2 驱逐与可恢复导航（Algorithm 1）
- 当工作视图超过预算 `ρC`（C为上下文窗口）时触发驱逐流程：
  1. 将活跃对话轮次持久化到事件日志。
  2. 保护活跃轮、最近尾部、最新工具结果。
  3. 将非保护区域中的已完成工具输出折叠为 `seq` 指针；
  4. 若仍超预算，按恢复成本递增选择最旧的完整 span 驱逐。
  5. 被驱逐 span 的 **headlines**（模型在每一步为响应撰写的简短标题：任务、状态、下一步动作、状态）进入**分层驱逐索引**。
- **驱逐索引（Eviction Index）**：
  - 是紧凑的地址锚定地图，使智能体能直接导航到已逐出区域，而非搜索整个日志。
  - 采用分层滚动合并（每层至多 `k` 块；满时最旧 `k-1` 块各自合并为一行并归入下一层），保证索引体积为 `O(k log_k n)`。
  - 较近的历史有细粒度锚点，较远历史用粗粒度区间表示，每个锚点都关联精确的 `seq` 范围，可完整恢复原始记录。

## 3. 实验设计

- **LOCA**：长上下文推理与行动；环境描述长度从 8K 到 256K tokens，评估智能体在增长环境中是否仍能正确推理和调用工具。

## 6. 主要结论与发现

- **Scroll 显著优于现有记忆系统与长时程智能体**：
  - LongMemEval_S：94.8%（与最佳系统 Exabase M-1 的 96.4% 相近，但超过 Mem0/Hindsight 等常用系统）。
  - BEAM_10M：73.1%，比最佳已发布系统 Exabase M-1 高 5.1 个百分点。
  - LOCA_128K/256K：89.3%/86.7%，比最佳已发布长时程智能体（MiniMax M3 + ReAct 的 49.3% 等）高 37.4 个百分点以上。
- **主干的编码能力决定上限**：所有主干都能使用 Scroll，但更强模型在需要长轨迹和复杂程序合成的 LOCA 上受益更大（86.7% vs 22.7%），而在简单查询型 LongMemEval_S 上差距小（94.8% vs 88.8%）。
- **核心优势来自无损日志与程序化访问**：消融显示，用有损摘要替换原始事件日志导致 BEAM_10M 总分崩塌至 19.9（尤其是信息抽取、时间推理、知识更新）；去掉持久内核损失 7.3 分；去掉驱逐索引损失 1.8 分但集中在需要跨分散证据的任务上。
- **失败模式明确**：在多会话推理、偏好跟随、总结类任务上可能弱于专门构建的消化式管线；失败主要源于查询表述不当（如聚焦错误轴）或位置化采样遗漏中部证据，而非底层记录不可达。
- **成本效率高**：BEAM_10M 的输入 token 中位数约 105K（约为语料 1%），输出远小于输入；基本没有摄取额外 LLM 调用。

## 7. 优点

- **概念创新**：将历史视为可执行环境而非待序列化文本，用代码代替固定记忆策略，推迟上下文选择到查询时，从根本上避免了不可逆信息丢失。
- **技术优雅**：仅追加日志 + 持久内核 + 驱逐索引的组合，自然实现无损、可追溯、可恢复。
- **算法高效**：驱逐索引分层滚动，索引体积对数级增长；搜索默认 BM25 无需向量模型推理，摄取无需 LLM。
- **工程可复现**：全部代码公开，提示词规则与案例轨迹均在附录中，便于复用与审计。
- **实验设计严谨**：同主干下的策略对比、跨模型测试、组件消融、成本记录、失败案例分析环环相扣。
- **应用前景**：可适配不同模型，并计划用前沿模型轨迹蒸馏到小模型，为后续优化提供了明确方向。

## 8. 不足与局限

- **基线对比非受控**：Table 2 中的记忆系统结果来自各系统自身配置，读者模型与评估设置不同，横向比较只能算参考。
- **某些能力弱于最佳系统**：在 BEAM 的“总结”“偏好跟随”“时间推理”类别，Scroll 低于 Exabase M-1 或 Hindsight；失败轨迹显示其查询程序仍依赖模型自主发现问题语义轴，容易在反直觉的偏好维度上“检索正确但答案错误”。
- **对模型编码能力依赖高**：能力较弱的主干在 LOCA_256K 上仅为 22.7%，说明 Scroll 无法弥补模型自身的计划与查询合成缺陷；这些任务可能还需要后训练或高级轨迹蒸馏。
- **长历史中的复杂推理仍薄弱**：多会话推理类别所有系统都低于 27%，Scroll 亦然；过度精确的过滤条件常导致证据集不完整。
- **评估广度有限**：LOCA 只有两个最大规模（128K/256K），未在更小尺度报告 Scroll；BEAM 只汇报了 10M 档，未展示 128K/500K/1M 的表现。
- **计算成本度量不完整**：仅报告 token 数与交互轮数，未报告延迟与美元成本，实际部署时的性价比还需进一步验证。
- **单次运行随机性**：默认每个任务只评估一次，未报告多次运行的方差，可能对结果稳定性造成影响。
