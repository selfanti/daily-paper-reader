## 摘要
可靠的多轮工具使用要求智能体保持不断演化的任务状态，并确保每个动作与其保持一致。然而，直接函数调用和ReAct风格策略在同一自回归轨迹中学习状态跟踪和动作生成。这种耦合造成了状态-动作竞争：生成下一个调用的压力可能会覆盖或忽略交互早期积累的信息。受Boyd的观察-定向-决策-行动循环启发，我们引入了OODA-Tool，一种类型化的闭环策略，通过将状态保持与动作实现分离来缓解这种竞争。OODA-Tool并非直接从交互历史中生成动作，而是将每个决策路由经过控制器检查的中间状态，确保最终输出基于当前任务状态。具体而言，观察阶段重构任务状态，定向阶段判断执行是否必要，决策阶段形成可接受的动作结构，行动阶段实现外部输出。我们使用从0.6B到14B的Qwen3模型，在多轮、多工具和不完整信息设置下，将OODA-Tool与直接函数调用和ReAct策略进行了评估。OODA-Tool在多种模型规模下持续提高了任务成功率，在较小模型上以及动作强烈依赖跨轮次和先前工具结果积累信息的任务上提升更大。受控变体、阶段级消融和迁移评估进一步证明了这些改进的稳健性。

## Abstract
Reliable multi-turn tool use requires an agent to preserve an evolving task state and ensure that each action remains consistent with it. However, direct function-calling and ReAct-style policies learn state tracking and action generation within the same autoregressive trajectory. This coupling creates state-action competition: the pressure to produce the next call can overwrite or ignore information accumulated earlier in the interaction. Inspired by Boyd's Observe-Orient-Decide-Act cycle, we introduce OODA-Tool, a typed closed-loop policy designed to mitigate this competition by separating state preservation from action realization. Rather than generating an action directly from the interaction history, OODA-Tool routes each decision through controller-checked intermediate states, ensuring that the final output remains grounded in the current task state. Specifically, Observe reconstructs the task state, Orient determines whether execution is warranted, Decide forms an admissible action structure, and Act realizes the external output. We evaluate OODA-Tool against direct function-calling and ReAct policies using Qwen3 models ranging from 0.6B to 14B across multi-turn, multi-tool, and incomplete-information settings. OODA-Tool consistently improves task success across model sizes, with larger gains on smaller models and on tasks whose actions depend strongly on information accumulated across turns and prior tool results. Controlled variants, stage-level ablations, and transfer evaluations further demonstrate the robustness of these improvements.

## 一、核心问题与整体含义（研究动机与背景）

- 论文聚焦于**多轮工具使用（multi-turn tool use）**的可靠性问题：智能体需要在使用搜索引擎、数据库、代码执行器、业务 API 等外部工具时，维护一个随交互不断演化的任务状态，并保证每个动作都与该状态一致。
- 现有方法存在一个关键缺陷：
  - **直接函数调用（direct function-calling）**与 **ReAct 风格策略**在同一自回归轨迹中同时完成“状态追踪”和“动作生成”。
  - 这种耦合会产生**状态-动作竞争（state-action competition）**：生成下一个工具调用的即时压力会覆盖或忽略早期交互中已经积累的信息，导致模型“看到最近一轮就回应”，却丢失了更早的约束、状态更新或工具反馈。
- 最终结果表现为：工具调用在语法上合法，但依赖过时或未经支持的信息；任务最终成功率可能很高，但中间决策与演化状态并不一致。
- 作者借用 Boyd 的 **OODA 循环（Observe–Orient–Decide–Act）**，主张将“状态保持”与“动作实现”分离，而不是让状态隐式地压缩在一次前向生成里。

## 二、方法论

### 核心思想
- 提出 **OODA-Tool**：一种类型化（typed）的闭环策略，将决策过程拆分为四个受控阶段，并由中央控制器逐阶段校验，使最终动作始终 grounding 于当前任务状态。
- 与单次生成式 agent 不同，OODA-Tool 不直接从交互历史映射到最终工具调用，而是先构造并检查中间状态，再执行输出。

### 四阶段流程
- **Observe（观察）**：基于交互历史重构任务状态，生成 provenance-aware 的“主动状态”，包括目标、实体、active slots、约束、证据来源、未完成子目标、近期工具事实和状态变化。
- **Orient（定向）**：判断当前状态是否足以执行动作，预测五类就绪模式：
  - `SOLVABLE_WITH_TOOL`
  - `NEED_CLARIFICATION`
  - `RESPOND_DIRECTLY`
  - `RECOVER_FROM_FAILURE`
  - `DONE`
  - 同时记录缺失参数、被违反约束、不可用工具，并在证据不足时阻止动作执行。
- **Decide（决策）**：在 Orient 允许的范围内，构造“动作结构”，如单次调用、顺序链或并行调用集合，并指定目标工具、调用顺序与数据依赖，但**不展开最终参数值**。
- **Act（行动）**：将动作结构编译为可用于外部环境的 schema 合法调用，完成参数绑定、引用解析、类型转换等，或输出澄清问题、直接回答、恢复动作与终止响应。

### 关键机制
- 中央控制器强制执行约束：
  \[
  z_t^D \in Z^D(z_t^R)
  \]
  即 Decide 阶段不能产生 Orient 未授权的动作结构。
- 公式化描述：
  \[
  z_t^O = f_O(h_t, T),\quad
  z_t^R = f_R(z_t^O, h_t, T),\quad
  z_t^D = f_D(z_t^O, z_t^R, h_t, T),\quad
  a_t = f_A(z_t^O, z_t^R, z_t^D, h_t, T)
  \]
- 三种模型变体：
  - **Joint OODA**：四个阶段输出在单次模型调用中串行生成。
  - **Shared OODA**：四次阶段调用，但共享同一个 LoRA 适配器。
  - **Specialized OODA**：每个阶段使用独立的 LoRA 适配器，共享冻结的 Qwen3 骨干网络。
- 训练目标采用 token 级交叉熵；监督标签按阶段顺序构建，并严格避免引入当前行动执行后才能获得的信息。
- 通过“typed-state bottleneck”测试状态充分性：将下游阶段的历史访问移除，只保留类型化中间状态和工具 schema，观察性能下降程度。

  - **MTU-Bench**：测试跨工具使用设置上的迁移能力。
  - **BFCL**：测试函数调用实现能力，包括 Overall、Non-Live、Live、Multi-turn 等轨道。

### 对比方法
- Baseline Instruct（无微调）

- ReAct-LoRA：先产生自由文本推理再行动

## 四、主要结果

### 主数据集（ToolDial）

- **Specialized OODA 显著优于所有基线**：在任务成功率和状态一致性上均领先 Direct-LoRA 与 ReAct-LoRA 约 5–10 个绝对百分点。
- **Shared OODA 也优于 Joint OODA**，证明多阶段调用本身比单次串联生成更有助于解耦状态与动作。
- **状态-动作竞争确实存在**：Direct-LoRA 在简单回合上表现良好，但在需要回溯早期工具结果的复杂多轮场景中错误率急剧上升；ReAct 虽通过自由文本缓解部分问题，但仍未彻底消除耦合。

### 迁移评估

- **FAIL-TaLMs**：OODA-Tool 在“何时需要澄清/恢复”的判断上显著优于基线，尤其在信息不足场景下减少幻觉性工具调用。
- **MTU-Bench**：三种 OODA 变体均展现出较强跨域工具组合能力；Specialized 版本尤其擅长并行调用依赖链较长的任务。
- **BFCL**：在 Non-Live 和 Multi-turn 轨道上表现突出；Live 轨道上与最强的 Direct 基线持平或略优，说明类型化状态并不会损害实时 API 调用的灵活性。

### 状态瓶颈测试

- 移除完整历史、仅保留类型化状态时，OODA-Tool 的性能下降很小（<2%），而 Direct/ReAct 在相同条件下性能大幅下降。
- 这说明 OODA 的中间状态确实**充分捕获了任务相关历史信息**，可以作为动作生成的独立 grounding 基础。

## 五、分析与讨论

- **阶段分离的价值**：强制模型先“说出”当前状态再决定动作，相当于显式推理正则化，减少了隐式状态追踪的负担。
- **类型化瓶颈的贡献**：通过固定状态结构（目标/实体/slots/约束/证据），模型难以跳过关键信息而直接输出动作，从而抑制了“看到最近一轮就回应”的捷径行为。
- **失败恢复能力**：Orient 阶段明确识别 `RECOVER_FROM_FAILURE` 模式，使模型能基于错误反馈重新规划，而不是在错误前提上继续调用工具。
- **效率权衡**：多阶段调用增加了延迟与 token 开销；Specialized 变体虽效果最好，但需要更多推理资源。论文通过消融实验表明，即使 Shared 或 Joint 结构也能带来大部分收益，为实际部署提供灵活选择。
- **局限性**：
  - 状态模式（readiness modes、状态字段）需要人工设计，可能难以覆盖全新任务类型。
  - 对大型语言模型的指令遵循能力依赖较高；较弱模型上阶段输出可能不稳定。
  - 实验集中于文本工具调用环境，尚未在图形界面或具身操作中验证。

## 七、结论

- 论文提出 OODA-Tool，一个将工具使用决策显式分解为 Observe–Orient–Decide–Act 四个阶段的闭环框架。
