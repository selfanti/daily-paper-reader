## 摘要
大型语言模型（LLM）智能体日益依赖长期记忆来支持多会话交互和个性化。然而，现有的智能体记忆系统被设计为仅前向演化，不断积累、整合和覆盖知识，缺乏检查、版本化或回退先前状态的原则性机制。这使得智能体在修正、概念漂移和记忆损坏面前变得脆弱，尤其是在它们已经暴露于后续信息之后。我们提出了ChronoMem，一个用于智能体记忆的语义版本控制层，集成到Google的生产级开源Agent Development Kit中。ChronoMem在每次记忆写入时提交全记忆快照，维护结构化版本历史，并通过混合词汇和语义检索、排名融合和重排序，将撤销意图映射到具体历史版本，从而支持自然语言回滚请求。我们进一步引入了一个事后暴露评估协议，测试智能体在回滚后是否能表现出反事实行为，即回答问题并总结历史，就好像未来更新从未发生过一样。在扩展了演化记忆状态和回滚任务的长时对话基准上，与仅提示和仅检索的基线相比，ChronoMem在回滚一致的问题回答和历史摘要方面大幅提升，同时在语义版本选择上实现了强劲性能。据我们所知，ChronoMem是第一个用于LLM智能体中系统性语义全局记忆回滚的开源系统和基准。

## Abstract
LLM agents increasingly rely on long-term memory to support multi-session interaction and personalization. However, existing agent memory systems are designed around forward-only evolution, continuously accumulating, consolidating, and overwriting knowledge, with no principled mechanism to inspect, version, or revert prior states. This makes agents brittle under corrections, concept drift, and memory corruption, particularly after they have already been exposed to subsequent information. We present ChronoMem, a semantic version-control layer for agentic memory integrated into the production-ready, open-source Agent Development Kit by Google. ChronoMem commits whole-memory snapshots at each memory write, maintains structured version histories, and supports natural-language rollback requests by mapping undo intents to concrete historical versions through hybrid lexical and semantic retrieval, rank fusion, and reranking. We further introduce a post-exposure evaluation protocol that tests whether an agent can behave counterfactually after rollback by answering queries and summarizing history as if future updates had never occurred. On long-horizon conversational benchmarks augmented with evolving memory states and rollback tasks, ChronoMem substantially improves rollback-consistent question answering and history summarization relative to prompt-only and retrieval-only baselines, while achieving strong performance in semantic version selection. To our knowledge, ChronoMem is the first open-source system and benchmark for systematic semantic global memory rollback in LLM agents.

### 一、论文的核心问题与整体含义

**研究动机与背景：**

- 大型语言模型（LLM）智能体日益依赖长期记忆来支持多会话交互与个性化服务，现代智能体框架从交互中提取事实、摘要和情节轨迹，持久化到外部存储或知识库中，形成一个持续演进的记忆状态。
- 然而，现有智能体记忆系统本质上是**仅前向演化**的：不断积累、整合、覆盖知识，没有原则性机制来检查、版本化或回退先前的记忆状态。
- 这种设计带来三个核心挑战：
  1. **错误累积**：一次错误的记忆写入会被后续检索不断放大，无法追溯到源头；
  2. **记忆中毒**：攻击者可通过注入恶意条目污染记忆库，诱导持久性的后门行为（AgentPoison）；
  3. **概念漂移**：用户偏好或事实更新后，旧的矛盾信息仍可能被检索到，且无法恢复"更新前"的可信状态。
- 现有商业服务（如Vertex AI Memory Revisions）仅支持不透明的版本ID回滚（`target_revision_id`），不提供语义化的自然语言回滚接口；ADK Session Rewind、OpenAI Agents SDK等框架工具仅支持会话级别的回滚，**明确不支持恢复全局长期记忆状态**。
- 论文的核心主张：**"回滚后的反事实行为"首先是一个系统架构问题，而非提示工程或检索增强能够可靠实现的能力。** 需要显式的、版本化的内存状态恢复机制。

### 二、论文提出的方法论

**核心思想：**

ChronoMem将LLM智能体的长期记忆视为一个**版本化状态机**：每次记忆写入生成一次全量快照（commit），支持通过显式版本ID或自然语言"撤销"请求将整个记忆状态回滚到任意历史版本，使后续所有读取被限定在该历史版本范围内，实现"记忆事实级撤销，如同后续交互从未发生"的效果。

**关键架构组件：**

1. **LocalMemoryService（编排器）** ：拦截记忆写入以创建版本，暴露两类回滚API：
   - `rollback_to_version(version_id)`：基于ID的确定性恢复；
   - `rollback_to_version_by_nl_query(query)`：通过混合检索将自然语言查询解析为目标版本后调用前者。

2. **SQLite内存存储**：持久化追加式事件日志、版本元数据和快照载荷，维护活动版本指针HEAD。

3. **Reranker模块**：使用更强的相关性模型（如交叉编码器）对候选版本进行重排序。

**四个阶段的技术流程：**

- **Stage (1) 版本构建：提交即写入（commit-on-write）**。采用事件溯源原则，每次写入追加不可变事件到日志L，物化全量快照S(vj)，存储元数据并推进HEAD指针。日志+快照设计避免了回滚时重放全部日志，以存储换恢复速度。事务性写入路径见Algorithm 1。

- **Stage (2) 版本索引：语义提交描述符**。为每个版本vj构建结构化描述符dj = {delta, summary, op, labels}，其中delta捕捉操作级变化，summary提供简洁的自然语言描述，op表示更新类型，labels包含时间元数据。检索在描述符层面进行，成本受版本数量限制，与快照大小无关。

- **Stage (3) 自然语言→版本映射：混合检索**。两阶段检索栈：
  - **词法检索**：SQLite FTS5 BM25对描述符排序；
  - **稠密语义检索**：嵌入描述符并取top-K；
  - **秩融合（RRF）** ：用倒数秩融合合并两个排序列表：

    RRF(vj|q) = Σ_{m∈{lex,sem}} 1/(k0 + rank_m(vj))，其中k0通常取60；
  - **重排序**：用交叉编码器对融合后的top-K候选重排，选出最终版本。

- **Stage (4) 版本回滚执行：基于ID的确定性恢复**（Algorithm 2）：加载快照载荷→恢复本地记忆状态→设置HEAD→截断后续版本以维持线性历史→同步检索后端索引。**选择与执行分离**的设计避免了将"选错版本"与"恢复错误"两类错误混为一谈。

### 三、实验设计

**数据集：**

- **LoCoMo**：长时多会话对话基准，含问题回答和事件摘要任务。使用其QA证据跨度（包含答案的对话ID）和会话级事件标注作为锚点。
- **MemoryAgentBench (MAB)**：增量多轮交互基准，正式定义了准确检索、测试时学习、长程理解、冲突消解四类能力。评估聚焦于准确检索子集和英文摘要任务（En.Sum）。

**评估协议（事后暴露回滚协议）：**

- **暴露阶段（Exposure）**：摄入完整交互流至最终状态vT；
- **回滚阶段（Rollback）**：发出自然语言回滚请求并恢复到目标版本v*；
- **执行阶段（Execution）**：在恢复的状态上执行下游任务（QA或摘要）。
- 该协议强制"反事实"要求：智能体已观察到v*之后的信息，但必须表现得如同仅存在回滚后的状态。
- 回滚查询通过"真实标注锚点+模板"与"LLM生成改写"两种方式构造，明确禁止使用版本ID、时间戳或会话索引，以避免平凡化版本选择。

**评估指标：**

- 语义版本选择：Recall@1、Recall@5（排名准确性）、Scope@2（时间邻接性，即选中版本与真实目标版本距离≤k的概率）；
- 回滚一致QA：Exact Match和/或F1，同时检测答案中是否包含v*之后的事实（违反一致性）；
- 回滚一致摘要：ROUGE-1。

**对比基线：**

1. **Prompt-only回滚**：仅提供自然语言回滚指令+任务查询，不改变底层记忆状态，测试纯指令遵循能力；
2. **Full-history提示回滚**：将完整交互历史（含v*后信息）输入模型并指示"装作已回滚"，测试最大污染下的推理抑制能力；
3. **Retrieval-only回滚（RAG-only）** ：用稠密相似搜索检索相关历史片段，不恢复版本化快照，隔离显式版本恢复与标准检索增强的效果差异。

**骨干模型：** Llama-3.1-8B、Qwen2.5-7B、Mistral-7B；交叉编码器使用Cohere Rerank-3.5。

### 六、论文的主要结论与发现

1. **语义版本选择（RQ1）** ：ChronoMem在LoCoMo上将Recall@1从12.0%（仅混合检索）提升至20.5%，Recall@5从28.1%提升至38.9%；在MAB上Recall@1从24.3%→33.4%，Recall@5从53.8%→60.2%。Scope@2提升尤为显著（LoCoMo 17.9%→31.2%，MAB 40.5%→58.0%），证明**混合融合本身不足，重排序阶段对消除相邻语义相似版本的歧义至关重要**。

2. **回滚一致QA（RQ2）** ：ChronoMem在所有骨干模型上均优于最强非版本化基线（RAG-only）。LoCoMo上F1提升约7-12个百分点（如Llama-3.1-8B：28.9%→36.1%）；MAB准确率提升约14-21个百分点（如Qwen2.5-7B：34.2%→55.1%）。**Prompt-only基线接近随机水平，证明事后暴露污染无法通过提示工程克服**。

3. **回滚一致摘要（RQ3）** ：ChronoMem在LoCoMo上ROUGE-1较最强基线提升0.03-0.04（如Llama-3.1-8B：0.21→0.25）；MAB上F1全面提升，全历史提示在此任务上优于RAG-only，说明**摘要任务依赖全局连贯性，小片段检索难以重建**。

4. **核心论断验证**：回滚一致行为主要是由显式版本化状态恢复带来的架构属性，不能可靠地从指令遵循或片段级相似性搜索中涌现。

### 七、优点

1. **填补空白**：首个开源、集成于生产级框架（Google ADK）的语义全局记忆回滚系统，使用得当。
2. **系统设计清晰**：事件溯源+快照的双轨设计兼顾审计性与恢复效率；语义描述符索引将检索成本与快照大小解耦；选择与执行分离使系统具有可解释性和可调试性。
3. **评估协议创新**："事后暴露回滚协议"是首个系统性检验回滚后反事实行为的评估标准，克服了传统前向记忆评测的局限。
4. **多模型交叉验证**：三个不同骨干模型的一致性结果增强了结论的稳健性。
5. **范围对比明确**：表1对ChronoMem与Vertex、ADK Rewind、OpenAI SDK、WebRollback在回滚目标、接口方式、开源性和公共评测四个维度做了清晰定位。

### 八、不足与局限

1. **并发与事务语义未经验证**：依赖SQLite单写者模型和每用户锁，多会话/多用户高频提交回滚时存在争用和排队风险。论文明确承认未评估高并发设置。
2. **仅支持线性历史**：回滚后截断后续版本（Git reset风格），不支持分支、合并或多时间线场景，限制了在需要"撤销但保留未来探索"场景中的实用性。
3. **基准适配的固有局限**：LoCoMo和MAB并非为回滚场景设计，构造的回滚查询基于"真实标注锚点+约束改写"可能无法涵盖真实用户回滚意图的多样性、歧义性和部分指定性。论文坦承结果展示的是受控条件下的架构稳健性，而非生产级部署的完整行为特征。
4. **缺少消融研究**：未隔离各组件（BM25、稠密检索、RRF融合、交叉编码器重排序）的独立贡献和交互效应。
5. **外部副作用未处理**：ChronoMem不撤销超出记忆基板的任意外部副作用（第三方服务、应用级资源），这与现有回滚机制的局限一致，但意味着在真实agent部署中，回滚一致性并不完整。
6. **算力信息缺失**：未公开训练/推理算力配置，影响可复现性和成本评估。
