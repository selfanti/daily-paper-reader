## 摘要
现代智能体运行在管理工具、上下文和控制流的智能体框架中，使得该框架成为智能体系统的关键组成部分。我们最初的Agent Lightning提出了一种解耦架构，通过LLM端点代理将任意智能体连接到RL训练，这一方法后来被verl、Uni-Agent、AReaL 2.0、slime和Polar等框架采用。我们将这种范式称为框架化智能体强化学习，其中部署时的框架直接参与模型后训练。框架化智能体强化学习与传统智能体强化学习有根本区别：框架而非训练引擎拥有环境交互循环，而训练器仅观察LLM请求-响应对的序列。这引入了重新分词、样本合并、优势计算、损失归一化和后端调度等方面的挑战，这些挑战可能显著影响训练的稳定性和有效性。我们提出了Agent Lightning v1.0，一个用于框架化智能体强化学习的轻量级框架，实现代码约3500行。它支持任意智能体框架，并作为研究这些挑战的实用测试平台。我们在指令遵循、搜索和编程智能体上对其进行评估，并为编程智能体强化学习提供了完整的可复现流程。仅使用6K训练样本和适度的计算资源，强化学习将Qwen3.5-9B在SWE-bench Verified上的性能从41.8%提升到56.4%，绝对增益达14.6个百分点。我们发布了完整的工作流程和训练脚本，以促进框架化智能体强化学习的可复现研究。

## Abstract
Modern agents operate inside agent harnesses that manage tools, context, and control flow, making the harness a critical part of the agent system. Our original Agent Lightning introduced a disaggregated architecture that connects arbitrary agents to RL training through an LLM endpoint proxy, an approach later adopted by frameworks such as verl Uni-Agent, AReaL 2.0, slime, and Polar. We refer to this paradigm as harnessed agentic RL, where the deploy-time harness directly participates in model post-training. Harnessed agentic RL differs fundamentally from traditional agentic RL: the harness, rather than the training engine, owns the environment interaction loop, while the trainer observes only sequences of LLM request-response pairs. This introduces challenges in retokenization, sample merging, advantage calculation, loss normalization, and backend scheduling, which can substantially affect training stability and effectiveness. We present Agent Lightning v1.0, a lightweight framework for harnessed agentic RL implemented in approximately 3,500 lines of code. It supports arbitrary agent harnesses and serves as a practical testbed for studying these challenges. We evaluate it on instruction-following, search, and coding agents, and provide a complete reproducible pipeline for coding-agent RL. Using only 6K training examples and modest compute, RL improves Qwen3.5-9B on SWE-bench Verified from 41.8% to 56.4%, a 14.6-point absolute gain. We release the complete workflow and training scripts to facilitate reproducible research on harnessed agentic RL.

## 1. 核心问题与整体含义（研究动机与背景）

- **核心矛盾**：现代智能体并非以独立 LLM 的形式运行，而是运行在智能体框架（agent harness）中——这些框架负责管理工具调用、上下文构造、控制流和错误恢复。因此，框架本身就是智能体能力的一部分，决定了智能体如何观察环境、如何在长程任务中行动、以及如何从失败中恢复。
- **传统 RL 训练的脱节问题**：早期 RL 框架（如 verl、AReaL、slime）要求用户直接在训练框架内部实现智能体循环，这与实际部署时使用的复杂智能体框架（如 mini-SWE-agent、OpenHands、Claude Code 等）无法直接兼容。若要将这些框架用于 RL 训练，必须在其内部重新实现完整的智能体逻辑，成本极高。
- **新范式的提出**：本文正式定义 **"harnessed agentic RL"（框架化智能体强化学习）** 这一范式：让部署时实际使用的智能体框架直接参与模型后训练。训练系统仅通过 LLM 端点观察请求-响应对序列，而框架仍持有上下文构造、工具执行和环境交互循环。这缩小了训练与部署之间的差距。
- **关键挑战**：该范式带来了传统 agentic RL 中不存在的新问题，包括重分词化、样本合并、优势计算、损失归一化和训练后端调度等。若处理不当，会导致训练不稳定甚至失效。现有框架对这些问题的处理方式各不相同，且普遍未作系统阐述。

## 2. 方法论：核心思想、关键技术细节

### 2.1 总体架构

Agent Lightning v1.0 采用**解耦架构**，由三个核心组件构成：

- **API Gateway（API 网关）**：有状态的服务，存储 rollout、模型和事件数据；对外提供 rollout API 和 proxy API。代理 API 将智能体框架的 LLM 调用转发到训练器注册的推理端点，并记录每次调用的 prompt token、response token 和 log-probabilities。所有端点设计为**幂等**，支持网络故障后的安全重试。
- **Rollout Controller（Rollout 控制器）**：管理智能体执行。通过 K8s Reconciler 在 Kubernetes 集群上调度标准 Job 运行智能体，或通过 Local Reconciler 在本地进程池中执行。API Gateway 的 rollout 状态是唯一事实来源，Kubernetes 状态与其实现尽力而为的最终一致性。
- **Customized Trainer（定制训练器）**：基于 VERL 构建，负责注册 rollout、等待完成、取回事件、组装训练样本。包含专用的 Sample Adapter（处理样本合并、优势计算、损失归一化）和轨迹监控系统。

### 2.2 传统 Agentic RL 与 Harnessed Agentic RL 的形式化差异

- 传统：训练引擎拥有环境交互循环，策略模型观察到的是连续扩展的 token 历史，`p_t = (p_{t-1}, a_{t-1}, o_t)`，一个 rollout 自然映射为一个线性 token 轨迹、一个训练样本。
- Harnessed：框架拥有环境交互循环，策略模型只观察到每次 LLM 调用时收到的 prompt。一个 rollout 被暴露为模型边界的请求-响应对序列 `C(ρ) = ((p1,a1), (p2,a2), ...)`，中间的环境与框架状态转换对外不可见。两者都可用 POMDP 建模，但隐状态和策略模型的观测不同。

### 2.3 核心挑战与设计选择

**挑战一：重分词化与样本合并**

- 即使文本不变，重新分词也会改变 token 边界。例如单词 "having" 第一次被采样为 `h` + `aving` 两个 token，但重分词后可能变成 `hav` + `ing`。这导致 token 级前缀连续性断裂（式 8 成立但式 9 不成立）。
- 断裂来源有三：(1) 聊天模板非组合性（渲染完整消息历史 ≠ 拼接各部分渲染结果）；(2) 解码-重分词漂移（Tok(Decode(a)) ≠ a）；(3) 推理时输出变换（工具调用解析、规范化、修复、重序列化）。
- 应对策略有四种：独立调用训练（正确但计算浪费）、缓冲 token 替换（可提高合并率但引入了 off-policy 拼接问题）、树结构训练（可复用前缀但后端复杂度极高）、**尽力而为序列合并**（仅在 token 级前缀精确匹配时合并，否则新开序列）。
- Agent Lightning v1.0 采用**尽力而为序列合并**：保证训练时使用的 prompt 与 rollout 中实际消费的 prompt 一致，且兼容标准密集因果核。

**挑战二：优势计算**

- 由于重分词、子智能体派生、上下文总结等原因，一个 rollout 可产生**动态数量**的训练样本。实验中平均每个 rollout 产生 2.41 个样本，仅 36% 的 rollout 保持为单个样本。
- 关键问题：GRPO 的组基线应在 rollout 级还是样本级计算？示例中，两个 rollout 奖励为 1 和 0，rollout 级基线 = 0.5，样本级基线 = 0.75。作者论证 **rollout 级优势计算**更合理——重分词和子智能体是偶然/内部操作，不应改变组基线。
- 论文指出 verl Uni-Agent 和 Polar 采用 rollout 级，而 slime 和 AReaL 采用样本级。

**挑战三：损失归一化**

- 动态样本数使损失归一化方式影响训练权重。比较三种方案：
  - `L_token-mean`（DAPO）：按 token 总数归一化；
  - `L_seq-mean`（GRPO）：先样本内平均再对所有样本平均——会给产生更多样本的 rollout 更大权重，作者认为这有问题；
  - `L_rollout-mean`（slime）：先 rollout 内 token 平均再对 rollout 平均。
- 作者认为 token-mean 和 rollout-mean 在理论上更合理，但实践中 token-mean 对长负样本敏感、易导致训练后期不稳定，因此**首选 rollout 级 token-mean 损失**。

**挑战四：训练后端调度**

- 一个 rollout 批次产生多少样本、多长序列，只有执行完成后才知道，但 GPU 数量和并行配置已固定。后端需将可变工作负载映射到固定 worker，同时保持每个序列的 rollout 标识和 prompt 组标识。
- rollout 内的序列必须留在同一次优化更新中，拆分会导致同一 rollout 的不同部分在不同策略版本下评估，产生策略偏斜。

### 2.4 工程创新：Collocated Async RL（协同部署异步 RL）

- 同步 RL 慢（等待最慢 rollout），异步 RL 需要更多 GPU（推理和训练分离部署）。
- 方案：**推理与权重更新时分复用同一批 GPU**。数据足够后开始更新，API Gateway 停止接受新请求并等待在途请求完成；新请求到来时暂停直至重新进入 rollout 阶段。切换对智能体框架完全透明。实验中比同步 RL 提速约 2 倍且所需 GPU 更少。

### 2.5 其他工程要点

- **网络可靠性**：所有 API Gateway 端点幂等；对共享相同 prompt 的多次 model_request 事件去重，仅保留最后一次。
- **Kubernetes 集成**：直接在自托管 K8s 集群上运行智能体，避免 Modal、E2B 等商业沙箱的持续成本。
- **监控**：记录训练/验证 rollout 及 K8s pod 日志，可用 AI 智能体自动诊断奖励黑客等问题。

## 6. 主要结论与发现

- **范式成立**：通过 LLM 端点代理将任意部署 harness 接入 RL 训练是可行且有效的，且该范式已被多个主流框架（verl Uni-Agent、AReaL 2.0、slime、Polar）跟进采用。
- **具体性能提升**：
  - 搜索智能体：验证奖励从 25.1% 提升至 41.7%（绝对 +16.6%）；
  - 通用指令遵循：验证奖励从 51.9% 提升至 70.2%（绝对 +18.3%）；
  - 编码智能体：SWE-bench Verified 从 41.8% 提升至 56.4%（绝对 +14.6%），仅用约 6K 训练样本。
- **设计选择验证**：rollout 级优势计算 + rollout 级损失归一化可获得最高验证奖励（38.2% vs 基线 35.0%），且策略熵增长更慢、更稳定。损失归一化能有效控制修正优势后引入的熵增。
- **动态样本数是实际现象**：编码智能体训练中平均每个 rollout 产生 2.41 个训练样本、仅 36% 的 rollout 保持为单样本，证实了所提挑战的实际重要性。

## 7. 优点

- **轻量简洁**：全系统约 3,500 行代码，以极简实现覆盖完整训练-执行链路，可读性与可复现性高。
- **问题识别精准**：首次系统性地阐述"重分词化导致 token 前缀断裂""动态样本数导致优势/归一化失真"等问题，并给出严格的公式化描述和直观示例，对社区有重要参考价值。
- **rollout 级统计原则**：主张样本数不应影响优势与归一化统计，这一观点在理论上更具原则性，消融实验也提供了实证支持。
- **工程实用性**：Collocated Async RL 在较少 GPU 下获得约 2 倍加速；幂等 API 与去重机制解决了网络不可靠问题；自托管 Kubernetes 避免了商业沙箱成本。
- **开源贡献**：公开完整数据清洗管道、训练脚本、奖励黑客防护措施，使编码智能体 RL 训练首次具备端到端的可复现流程。
- **奖励黑客防护**：识别出 4 类具体奖励黑客行为并给出针对性防护（禁用 git、网络白名单），对后续研究有直接借鉴价值。

## 8. 不足与局限

- **算力信息不透明**：未说明 GPU 型号、数量、训练耗时，难以评估复现门槛和资源效率的绝对值。
- **对比实验缺失**：未与现有同类框架在相同条件下做基准对比，无法客观评估 Agent Lightning v1.0 相对 verl Uni-Agent、slime 等的系统级优劣。
- **数据过滤偏差**：SWE-smith 的难度过滤使用训练模型自身进行"四轮求解"判定，可能引入模型偏好和分布偏移；移除测试数>200的任务也会让训练分布偏向小型仓库。
- **评测范围有限**：SWE-bench Verified 只是编码智能体的经典基准，未覆盖更难的 SWE-bench Full；搜索智能体采样量较小（每数据集 50 例）；无长时程训练（

无长时程训练（如 500 步以上或更大 batch size 的 scale-up 实验），也未报告训练曲线的完整走向与方差的多次运行结果，使结论的稳健性和可扩展性仍缺少充分证据。
- **部分术语与实现细节未展开**：论文虽称训练器基于 VERL，但未明确说明与上游 VERL 的代码差异、具体使用的 kernel/注意力实现，也未深入讨论长上下文场景下尽力而为序列合并带来的显存碎片与计算冗余问题。
- **reward hacking 防护深度有限**：针对已在编码任务中发现的 4 类“灰色路径”做了防护，但仅针对 SWE-bench 类任务；是否有未发现的旁路（如通过 shell 别名、SSH 代理访问 git 等）未作压力测试。对通用指令遵循场景的安全防护则更加薄弱。
- **样本合并策略的固有局限**：尽力而为合并只复用精确匹配 token 前缀，仍存在大量计算浪费；而缓冲 token 替换虽能提高合并率，却引入 off-policy 拼接偏差。作者选择更保守的方案，但其实际计算开销削减程度未量化。

## 9. 对社区的启示与可复现性

- **可复现性评估**：
  - 论文在 GitHub 开源全部代码、数据清洗/训练脚本、奖励黑客防护配置，并对数据集容器镜像体积、K8s 网络策略等做了具体说明，这是当前 agentic RL 论文中少有的高透明度。
  - 但训练所用 GPU 种类、数量、训练时长均未披露；且 SWE-smith 过滤后的 6K 样本集是否随代码一并发布尚未明确，若只靠读者自行复现过滤流程，则结果可复现性会打折扣。
  - 智能体执行的随机性（LLM 采样、测试输出排序等）对最终 pass@1 的影响未作方差分析，因此读者难以判断 56.4% 与 41.8% 之间的差距是否显著。

- **工程启示**：
  - **API Gateway 模式是关键的架构分界点**：它让 RL 训练系统与智能体 harness 彻底解耦，只需要 LLM 端点协议即可整合任意框架——这本质上把“LLM 运行时”而非“智能体运行时”暴露给训练器。这一设计值得被后续系统直接复用。
  - **rollout 级优势与归一化可视为一条新的社区默认规范**：动态样本数问题在强化学习理论中对应的是“episode 级统计量”，Agent Lightning 的探索为 GRPO 类算法在 harnessed 范式下提供了一个更稳妥的默认选择。
  - **Collocated Async RL 是资源受限实验室的重要参考方案**：时分复用 GPU 让推理与训练交替使用同一批卡，以略微增加的等待时间为代价换取了约 2 倍吞吐，是工程权衡的优秀案例。

## 10. 综合评价

Agent Lightning v1.0 的价值不仅在于它搭建了一个可用的训练系统，更在于它**第一次用清晰的抽象真正拆解了“agentic RL”这一模糊概念**，并将其落实为：一个可观察 LLM 边界的 API 网关、一个尽力而为的序列合并器、一套 rollout 级统计约定、以及一个时分复用的训练/推理调度器。它把过去散落在各框架实现中的隐性 trick（重分词处理、样本合并、归一化选择）显式化、系统化、工程化，论文也因此具有方法论层面的指导意义。

从学术严谨性看，论文的消融实验设计合理、变量控制较好，但缺少与现有框架的横向对比及重复实验统计，限制了对结论强度的判断。从工程实践看，代码轻量（约 3500 行）、关注真实痛点（网络故障、奖励黑客、GPU 成本），具有很高的落地参考价值。整体而言，这是一篇**“系统+方法”双重贡献、偏工程驱动但理论关切明确**的高质量论文，其核心思想（让部署 harness 直接参与训练、按 rollout 而非样本做统计）预计将成为该领域后续工作的默认出厂设置。
