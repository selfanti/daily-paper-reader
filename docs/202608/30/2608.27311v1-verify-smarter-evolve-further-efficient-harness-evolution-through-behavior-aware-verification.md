## 摘要
智能体框架决定了语言模型智能体如何使用指令、工具和运行时组件，但调整这些框架需要昂贵的验证。现有的“提出-验证”方法通常在一组固定的任务上对每个候选进行评分，将大量交互浪费在无关行为上，并让总体分数掩盖特定性能回退。我们提出了 HarnessLens，一个预算感知的自动化框架演化框架。HarnessLens 联合探索任务空间和用户可配置组件，从执行轨迹中推导候选修改，并通过可归因证据门控在行为相关任务上选择性验证每个候选。在三个智能体框架和四个基准测试中，HarnessLens 将平均保留性能提升了 7.6%–13.6%，同时消耗的评估预算远少于对比基线。这些结果表明，带有显式归因的行为感知验证能够在受限交互预算下实现更可靠且样本高效的框架演化。我们的代码可在 https://github.com/jhxu5214/HarnessLens 获取。

## Abstract
Agent harnesses shape how language-model agents use instructions, tools, and runtime components, but adapting these harnesses requires costly verification. Existing propose-and-verify methods typically score every candidate on a fixed task set, wasting rollouts on unrelated behaviors and allowing aggregate scores to obscure specific regressions. We introduce HarnessLens, a budget-aware framework for automated harness evolution. HarnessLens jointly explores the task space and user-configurable components, derives candidate modifications from execution trajectories, and selectively verifies each candidate on behavior-relevant tasks using an attributable-evidence gate. Across three agent harnesses and four benchmarks, HarnessLens improves average held-out performance by 7.6-13.6% while consuming substantially less evaluation budget than competing baselines. These results demonstrate that behavior-aware verification with explicit attribution enables more reliable and sample-efficient harness evolution under constrained interaction budgets. Our code is available at https://github.com/jhxu5214/HarnessLens.

## 2. 论文提出的方法论：核心思想、关键技术细节、公式或算法流程

### 2.1 核心思想

论文提出 **HarnessLens**，一个预算感知的自动化 harness 演化框架，核心思想是**行为感知验证（Behavior-Aware Verification）+ 可归因证据门控（Attributable-Evidence Gate）**：
- 为每个候选修改**选择与其行为效应相关的验证任务**，而非在所有任务上无差别评估；
- 仅当改进能够**归因于该修改**时才接受候选，防止噪声或聚合指标掩盖真实问题。

### 2.2 问题形式化

论文对关键概念进行了形式化定义：
- **组件与 Harness**：harness 框架 `F` 暴露一组用户可配置组件 `C_F = {c_1, ..., c_m}`；具体 harness 表示为 `H = <F, h>`，其中 `h` 是各组件配置的联合。
- **智能体**：`A_{θ,H} = (M_θ, H)`，由基础语言模型 `M_θ` 在具体 harness `H` 内运行。
- **修改与候选**：修改 `δ` 作用于组件配置空间，应用后产生候选 harness `H' = <F, δ(h)>`。
- **优化目标**：在固定交互预算 `B` 约束下，找到最大化期望任务成功率的演化后 harness：
  - `H* = arg max_{H ∈ H_F} E_{x∼D, τ∼p(τ|x;M_θ,H)}[R(x, τ)]`
  - 约束条件：`C(H_0 ⇝ H) ≤ B`
  - 其中 `R(x,τ) ∈ {0,1}` 为二值任务成功奖励，`C(H_0 ⇝ H)` 表示演化过程中消耗的 LLM 会话数和任务试验数。

### 2.3 方法三大阶段

HarnessLens 包含三个核心组件：

1. **上下文探索（Context Exploration）**：
   - **任务空间探索**：仅通过任务查询、环境指令、工具描述等信息组织训练任务，按主要用户目标分组，不执行任何任务；
   - **Harness 空间探索**：检查框架配置、文档和运行时行为，识别所有用户可配置组件及其更新机制、影响范围，为后续行为-组件归因提供基础。

2. **轨迹诊断（Trajectory Diagnosis）**：
   - **经验提取**：将轨迹总结为可复用经验和反复出现的缺陷，每条证据关联到支持它的轨迹；
   - **经验分析**：结合任务分组和组件清单，推导修改提案，检查支持轨迹是否提供充分证据，筛选掉缺乏支持的提案。该模块在初始 rollout 和每次验证 rollout 后都会执行，每个 rollout 既评估当前候选，又为未来演化积累证据。

3. **Harness 演化（Harness Evolution）**：
   - **候选提案**：演化代理基于支持证据、预算剩余量等选择提案，从当前确认的 harness 派生候选；
   - **行为感知验证**：针对每个候选修改选择与目标行为相关的训练任务（至少 5 个不同任务），并在当前 harness 和候选 harness 下使用匹配的试验条件进行评估；
   - **审查与更新**：演化代理基于行为证据与指标决定接受、拒绝或修订候选。接受需满足：存在可归因的正向证据、无可归因的回归、且在确认批次上主指标改善。未达门槛的候选导致 harness 不变（即平局），而非性能退化。

### 2.4 预算控制机制

- 总预算 `B = 200` 个交互单位（LLM 会话 + 任务试验均已计入）；
- 初始 rollout 消耗 `30 tasks × 2 trials = 60` 单位；
- 验证单个候选的固定成本为 6 单位 + rollout 成本 + 行为比较成本；
- 控制器在每次迭代前检查剩余预算是否足够完成"验证 + 确认"两轮以及 3 单位重试缓冲，不足则终止演化。

## 6. 论文的主要结论与发现

1. **HarnessLens 在最小预算下取得最佳性能**：在 12 组 harness–基准配置中有 8 组取得最佳或并列最佳 pass@1，使用的预算仅为 HarnessFix 的三分之二、Self-Harness 的四十分之一。
2. **性能改进显著**：平均留出性能提升 7.6%–13.6%（OpenCode 上最高 13.6%，Codex 上 7.6%，Pi 上 9.2%）。
3. **演化稳定可靠**：HarnessLens 从未低于初始 harness，最差结果也是平局（即保持不变）；相比之下，Self-Harness 和 Meta-Harness 在 24 组配置中有一半低于 H₀，最多损失约 10 个点。行为感知验证充当了"过滤器"而非"搜索加速器"。
4. **更多验证 rollout 不等于更好的 harness**：Self-Harness 使用最多 rollout 但性能并非最强；关键在于候选接受机制——聚合指标可能积累有害编辑，而可归因证据门控能防止噪声提升被保留。
5. **任务多样性的影响**：在 BIRD 中，相关任务暴露了共享的 SQL 决策点，支持可归因的修改接受；而 Terminal-Bench 2.0 的任务目标和执行路径更为多样，广泛适用的修改难以找到，保留原 harness 往往更优。

## 7. 优点

- **问题定位精准**：指出现有 propose-and-verify 范式"同一任务集验证所有修改"的根本缺陷，并给出系统性解决方案；
- **方法设计精巧**：将验证任务选择与每个修改的行为效应关联，形成"行为→组件→任务→证据"的完整归因链；
- **预算感知设计**：显式建模交互预算，所有环节（探索、诊断、演化、验证、确认）统一计入成本，预算核算透明审慎；
- **证据复用机制**：验证阶段的轨迹不仅用于当前候选审查，还被诊断模块提取为未来演化的经验，实现"一鱼多吃"的样本效率；
- **安全性保障**：可归因证据门控严格防止无证据支持的修改被接受，HarnessLens 在所有实验中"从不低于初始 harness"；
- **信息边界严谨**：各模型角色有严格的可见/排除信息划分（如表 3），防止 TEST 信息泄漏；
- **实验分析深入**：主实验之外还包含消融、决策级重评分、预算分配拆解、演化轨迹案例等多维度分析。

## 8. 不足与局限

- **实验覆盖有限**：仅使用一个模型家族（deepseek-v4-flash-preview）、三个 harness 和四个公共基准，对更广泛的模型、harness 架构和开放式部署环境的有效性尚未充分验证；
- **算力成本未归一化**：预算以交互单位计数，未归一化 token 使用量、延迟或货币成本，不同方法间的真实计算成本比较可能不完全公平；
- **消融范围偏窄**：行为感知批次选择和可归因门控的消融仅在 OpenCode 上验证，缺乏跨 harness 的一致性证据；
- **统计严谨性不足**：未报告多次运行的标准差或显著性检验，单次运行结果可能受随机性影响；
- **任务多样性带来的限制**：当基准任务多样性较高时（如 Terminal-Bench 2.0），缺乏可在 TRAIN 上获得充分支持的广泛适用修改，演化效果受限；这既是方法的局限，也是任务本质的挑战；
- **验证批次规模偏小**：最少仅 5 个任务，对于某些修改可能无法充分捕捉其行为效应；
- **外部工具与检索被禁用**：为保证公平性禁用了 web 搜索等外部信息检索工具，与真实部署环境存在差异；
- **基线预算口径差异**：HarnessLens 的预算包含了所有 LLM 会话，而基线只计算 rollout 数量，直接比较虽然有利于本文，但在附录中已作说明，仍需注意口径的一致性。
