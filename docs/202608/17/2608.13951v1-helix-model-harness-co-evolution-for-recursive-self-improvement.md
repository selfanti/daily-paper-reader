## 摘要
扩展智能体能力的研究大多聚焦于改进模型，然而交互式智能体通过运行时框架（runtime harness）来执行，该框架调节上下文、工具、控制流和停止条件。运行时框架既决定了模型能完成什么，也决定了模型学习所用的轨迹。这种耦合催生了面向递归自我改进的模型-运行时协同进化：为固定模型构建运行时框架，从经过验证的同类轨迹中更新模型，并随着模型能力的变化重建运行时框架。实现这一循环需要一种受控的方式来演进运行时框架，同时保持干预的一致性和效果。我们提出了HELIX，一个用于运行时框架进化的可溯源基础平台。HELIX将智能体系统分解为类型化端口、可复用原子、配方、产品外壳和运行时策略。它使干预明确且可审计，同时保留轨迹、测试结果和来源信息。因此，运行时框架进化扮演着两个相互关联的角色：改进固定模型的执行，并产生匹配的成功、回归、近似失败和替代解决方案，作为后续模型改进的数据。我们在代码修复任务上进行了一轮进化评估。一个包含65个候选的portfolio发现了一个固定运行时框架，将任务覆盖率比Pi提高了4.0%，而完整portfolio通过互补的同类行为暴露了多达58.0%的额外已验证覆盖率。选定的候选者通过重复运行和SWE-bench评估器进行评估。一个200槽位的同类切片生成了438条经过验证的SFT、评论家、过滤器和偏好记录。这些结果表明运行时框架、模型和数据如何形成一个反馈系统：运行时框架进化扩展了当前能力，并为下一个模型创造了学习信号；模型更新则推动下一轮运行时框架进化。HELIX为研究这一递归过程提供了可审计的接口。代码可在https://github.com/HKUDS/HELIX获取。

## Abstract
Scaling agent capability has largely focused on improving the model, yet an interactive agent acts through a runtime harness that mediates context, tools, control flow, and stopping. The harness shapes both what a model can accomplish and the trajectories from which it learns. This coupling motivates model-harness co-evolution for recursive self-improvement: build harnesses for a fixed model, update the model from verified sibling trajectories, and rebuild the harnesses as model capabilities change. Realizing this loop requires a controlled way to evolve harnesses while preserving intervention identity and effect. We present HELIX, a source-traceable substrate for harness evolution. HELIX decomposes agent systems into typed ports, reusable atoms, recipes, product shells, and runtime policies. It makes interventions explicit and auditable while retaining trajectories, test outcomes, and provenance. Harness evolution thus serves two linked roles: improving fixed-model execution and producing matched successes, regressions, near misses, and alternative solutions as data for subsequent model improvement. We evaluate HELIX in one evolution round on code repair. A 65-candidate portfolio discovers a fixed harness that improves task coverage by 4.0% over Pi, while the full portfolio exposes up to 58.0% more verified coverage through complementary sibling behavior. Selected candidates are assessed with repeated runs and the SWE-bench evaluator. A 200-slot sibling slice yields 438 verified SFT, critic, filter, and preference records. These results show how harness, model, and data form a feedback system: harness evolution expands current capability and creates learning signal for the next model; model updates motivate the next round of harness evolution. HELIX provides an auditable interface for studying this recursive process. Code is available at https://github.com/HKUDS/HELIX.

### 1. 论文的核心问题与整体含义（研究动机和背景）

- **核心问题**：智能体（Agent）能力的规模化提升不应只聚焦于改进模型本身。一个部署的智能体是“模型-运行时对”（model–runtime pair），模型必须通过一个运行时框架（harness）来执行任务——该框架负责上下文构建、工具接口、权限控制、重试/压缩策略、停止条件等。
- **被忽略的关键因素**：现有研究大多把 harness 视为“中性包装”，但本文认为 harness 是行为的共同决定因素（co-determinant），它决定模型观察到什么、能采取哪些动作、如何从失败中恢复、何时停止，因此直接决定智能体可完成任务的边界。
- **递归反馈机制**：harness 不仅影响模型当前执行，还塑造模型未来学习的轨迹数据。模型能力提升后，其偏好的 harness 设计可能随之改变。模型与 harness 之间的双向依赖构成了递归自我改进（RSI，Recursive Self-Improvement）的关键反馈回路。
- **本文主张**：应把“模型-运行时协同进化”（model–harness co-evolution）作为递归自我改进的一等原则，通过显式的 **build–update–rebuild** 循环，使系统状态 `Zt = (Mt, Φt)` 在每一轮迭代中重新进入下一轮改进过程，达成可审计、可验证的系统级自我提升。

### 2. 论文提出的方法论：核心思想、关键技术细节

#### 2.1 核心思想：两个耦合的反馈时间尺度

- **任务内快速循环（fast loop）**：harness 构建观测与动作接口，模型输出消息与工具调用，harness 执行并检查动作、返回环境反馈、决定是否继续。轨迹分布：
  `τt,i,x,k ~ P(τ | x, Mθt, Hφi, k)`
- **跨轮慢速改进循环（slow loop）**：验证器（verifier）对轨迹输出标签（resolved、regression、near-miss、policy violation 等），这些标签化的经验数据用于更新模型，并在下一轮重建 harness 组合：
  `Dt = G(Et), θt+1 = U(θt, Dt), Φt+1 = B(Φt, Et; Mθt+1)`
- **双目标优化**：harness 演化同时追求两个目标：
  1. **部署目标（执行）**：找到对当前模型最优的固定 harness，优化 `Jdeploy = E[R(y,τ) - λC(τ) - μP(τ)]`
  2. **数据目标（学习）**：候选组合产出结构化“兄弟轨迹集”（sibling set）：`St,x = {(Hφi, τ, y)}i,k`，为模型更新提供 SFT、critic、filter、preference 等多类型训练数据

#### 2.2 关键技术细节：HELIX 系统

HELIX 是一个源头可追溯（source-traceable）的 harness 改造平台，核心机制包括：

- **Harness 八维结构化表示**：
  `H = (H_shell, H_session/hooks, H_config, H_prompt, H_tools, H_turn, H_accept, H_policy)`
  覆盖了模型面对界面（prompt/tools）和环境控制面（权限、回合循环、接受条件）。

- **六种实体模型**：
  - **Port（端口）**：稳定能力槽位
  - **Atom（原子）**：通用原子提供产品无关行为，个性原子保留源码特定语义
  - **Pack（包）**：扩展一组便捷原子
  - **Recipe（配方）**：将原子、策略、shell 绑定为一个声明式候选
  - **Product Shell（产品壳）**：通过 SDK/CLI/TUI/Web 暴露候选
  - **Compiler & Lockfile**：保留与实际 rollout 完全对应的完整展开

- **设计空间与枚举**：每个完整产品合约暴露 **96 个端口/绑定/交换点**。基于 4 个开源 harness（OpenCode、Pi Mono、Nanobot、Hermes Agent）抽取行为。将 session/hooks 与 acceptance 绑定到 turn loop 后剩下 5 个独立来源选择，定义 **4⁵ = 1,024** 个候选；独立选择 acceptance 时为 **4⁶ = 4,096** 个。

- **预执行检查**：编译器执行依赖解析、端口绑定验证、并发/边界/源纯度检查，通过后生成确定性 lockfile，保证干预可执行、可审计。

- **证据平面（Evidence Plane）**：保留每次运行的配方与 lockfile、模型-任务-尝试身份、运行时轨迹、工作区 diff、验证器结果、策略证据，完整保存结果丰富度而非坍缩为单一成功位。

- **运行时交互流程**：会话恢复→提示/上下文构建→provider 流式推理→工具预检与权限检查→批量执行→验收证据评估→继续/停止决策→持久化轨迹与工作区快照。

- **Build–Update–Rebuild 闭环**：构建（为固定模型生成可追溯 harness 候选）→ 更新（验证后兄弟轨迹转为训练记录并更新模型）→ 重建（更新后模型的能力剖面可能偏好不同 harness 设计）。

### 6. 论文的主要结论与发现

- **发现 1：harness 演化能改善当前执行**。65 候选矩阵中，最佳固定配方解决 52/100（相对 Pi 的 50/100 提升 4.0%）；重复运行下 OpenCode 家族成员达到 75/100（Pi 为 72/100）；官方 SWE-bench 下最强成员解决 46/55（Pi 为 44/55）。但不同验证协议下最优成员不相同，说明不存在单一万能 harness。
- **发现 2：快速演化扩展执行广度与多样性**。完整 portfolio 事后联合覆盖 79/100 任务，比 Pi 多 29 个任务（相对提升 58.0%）；但 23/64 的非基线候选解决 0 个任务，说明任意组合不可靠，需要类型化门控、廉价筛选和自适应选择来利用互补性。
- **发现 3：兄弟对比转化为模型更新数据**。200-slot 精选切片（20 个实例 × 10 sibling slots）物化为 438 条训练记录：Clean SFT 63 条（14.38%）、Cleanup-needed SFT 56 条（12.79%）、Critic negatives 52 条（11.87%）、Filter samples 113 条（25.80%）、Preference pairs 154 条（35.16%）。
- **案例验证**：Sphinx 案例展示 harness 演化带来新的验证正样本；Pytest 案例证明“只过目标测试”不可作为安全正样本（存在回归仍被判 gaps-found）；Xarray 案例说明“补丁干净≠语义正确”（hygiene 相同但 fallback 语义不同导致结果迥异）。
- **核心结论**：模型、harness 和数据构成耦合改进系统——harness 演化既提升当前执行，也产生下一模型的训练信号；模型更新反过来驱动下一轮 harness 重建。系统改进单位应为 `Zt = (Mt, Φt)` 而非模型本身。

### 7. 优点：方法与实验设计亮点

- **概念上的重要纠正**：将 harness 从“中性包装”重新定位为“行为共同决定因素”，并系统化地将其纳入 RSI 框架，解决了一个被主流研究忽视的重要不对称问题。
- **源头可追溯的组件化设计**：将 4 个异构开源 harness 统一分解为端口/原子/配方/产品壳/策略，使干预从隐式 prompt hack 变为显式可审计对象；96 端口 × 4,096 配方的设计空间同时具备广度和可控性。
- **双输出框架清晰**：每个 harness 演化轮次明确产出两个产物——(1) 当前执行改进、(2) 验证后的兄弟轨迹数据，用同一套实验同时衡量两个产物，避免了将二者割裂的常见做法。
- **证据平面设计**：不把验证结果坍缩为单一成功位，保留轨迹、测试结果、策略决策、来源与结果标签；由此区分 resolved、regression、near-miss、policy violation 等细粒度标签。
- **数据物化多样性**：将同一组兄弟姐妹轨迹映射到 SFT、critic、filter、preference 四种训练目标，且按实例切分数据（防止相似轨迹在 train/dev 间泄漏）。
- **实验纵深设计**：从单次大规模矩阵→选定成员重复验证→官方 evaluator 交叉验证→具体案例 trace 级分析，形成递进式证据链。
- **案例选择平衡**：刻意包含正向（Sphinx 增益）、负向（Xarray 语义未命中）、回归（Pytest 目标通过但回归失败）三类对比，避免“更活跃 harness 更好”的单调叙事。

### 8. 不足与局限

- **实验覆盖局限**：
  - 仅评估代码修复智能体（AtCoder + SWE-bench 55 实例），不适用于泛化的智能体类型（通用对话、工具使用、多智能体协作等）。
  - 主实验使用 LCB 的公开测试，未测隐藏测试；100 个任务取的是前 100 个满足条件的样本而非随机抽样。
- **因果归因不足**：每个配方一次性改变多个组件，无法判断真正的驱动组件；作者自己也承认需要逐步改变单个组件来进一步验证。
- **尝试次数与协议不对称**：主矩阵 1 次/task，重复验证 10 次/task，SWE 验证 2 次/task，三种排名的可比性不足；Oracle coverage 是事后计算的，不能代表部署前的选择能力。
- **数据规模与闭环未完成**：训练数据仅 438 条记录且没有实际训练更新模型，未完成 multi-round 的 build–update–rebuild 闭环验证；数据集需扩大后才能令人信服地评估模型更新效果。
- **自动化评估的局限**：测试无法覆盖所有需求——补丁可能修改测试、做多余编辑或利用评估器漏洞；正确补丁也可能因超时/环境问题被误判。
- **安全与维护风险**：不同 harness 组合可能创造不安全权限组合；实验需隔离工作区、限制网络与权限、对轨迹做脱敏；上游 harness 更新后需重新测试集成与安全检查。

### 9. 总结性评价

HELIX 的核心贡献在于提供了一个可审计的“harness 演化和数据交接”接口，把 RSI 从抽象目标落实为可重复的工程过程。虽然论文的单轮实验数据规模有限、因果归因不足、闭环尚未完成，但“模型-运行时协同进化”的概念框架和“构建-更新-重建”的操作范式为未来多轮递归自我改进研究奠定了扎实的基础。其源头可追溯性、细粒度证据保留和兄弟轨迹驱动的多目标数据导出，是该领域一项值得关注的重要方法论贡献。
