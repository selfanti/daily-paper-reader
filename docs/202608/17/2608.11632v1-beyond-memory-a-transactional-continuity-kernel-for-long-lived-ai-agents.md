## 摘要
持久性AI代理在长时间跨度内累积版本化状态，但仅靠存储保留并不能识别权威状态。缺乏显式控制平面时，模型、工具和后台工作进程未经协调的更新可能导致过期覆盖、未经审计的暴露以及自我授权的权限提升。我们认为代理状态治理是一个基础设施激活问题，将连续性定义为已接受分支头的不间断、经授权的谱系。我们提出了连续性内核（CK），一种激活契约，将非提交式候选评估与原子状态激活解耦。不可信组件针对确切的前驱头或类型化缺失提出类型化更改。一个简短的激活事务会重新验证所有权、前状态权威、新鲜度和效果唯一性，并记录一个稳定处置（提交、拒绝、隔离或延迟）。仅“提交”会原子地推进分支头并安装完整的已接受单元（状态、权威、谱系、效果、结果和收据）。一个有界可执行模型遍历了2,808,230个可达状态和5,526,474次状态变更转换，验证了该协议，且未发生任何不变量违反。

## Abstract
Persistent AI agents accumulate versioned state across long horizons, but storage retention alone does not identify authoritative state. Without an explicit control plane, unmediated updates by models, tools, and background workers risk stale overwrites, un-audited exposures, and self-authorizing privilege escalation. We argue that agent state governance is an infrastructural activation problem, defining continuity as an unbroken, authorized lineage of accepted branch heads. We present the Continuity Kernel (CK), an activation contract that decouples off-commit candidate evaluation from atomic state activation. Untrusted components propose typed changes against an exact predecessor head or typed absence. A short activation transaction revalidates ownership, pre-state authority, freshness, and effect uniqueness, recording one stable disposition (Commit, Reject, Quarantine, or Defer). Only Commit atomically advances the branch head and installs the complete accepted unit (state, authority, lineage, effects, outcome, and receipt). A bounded executable model verifies the protocol across 2,808,230 reachable states and 5,526,474 state-changing transitions with zero invariant violations.

## 1. 论文的核心问题与整体含义

- **背景**：长期运行的 AI 代理会在多个上下文窗口之外积累记忆、用户画像、计划、工具状态和策略等版本化状态。然而，现有的代理记忆系统主要关注**检索质量**，检索到的高质量内容并不回答“哪个版本是权威状态”的问题。
- **核心问题**：
  - 模型、工具、压缩器（compactors）、后台恢复工作者可能并发或冲突地提交更新；
  - 存储层即使保留所有版本，也可能接受过期重试、暴露未提交状态、或允许提案通过向自身状态注入权限来实现“自授权”；
  - 存储保留（retention）本身并不等于权威（authority）。
- **核心论点**：代理状态治理本质上是一个**基础设施激活问题**，而非语义或检索问题。作者将**连续性（continuity）**定义为“一个分支上已接受头部的不间断、经授权的谱系”，这是一种关于状态激活和线性来源的基础设施保证，不是关于意识或行为同一性的哲学主张。
- **整体含义**：提出 Continuity Kernel (CK) 作为激活契约，将“候选生成”与“原子激活”分离，只有确定性控制面才能推进权威分支头。

## 2. 论文提出的方法论

### 2.1 核心思想
- 将**不可信的提议者**（模型、工具、操作者）与**受信任的激活控制面**严格分离。
- 提议者可以在提交前进行概率推理、网络获取、候选构造，但只有 CK 控制面可以通过一个“短事务”原子地推进权威分支头。
- CK 不发明新的底层事务引擎，而是复用关系数据库事务、条件对象清单或共识状态机日志等标准基板，在其内部执行激活契约。

### 2.2 系统模型
- 代理状态按分支组织：`k = (sid, bid)`，分支索引状态 `X[k]` 包含完整类型化组件（记忆、用户资料、工具配置、策略对象等）。
- 分支目录维护头部 `h` 和分支行 `B[k]`，其中包含 `root`（状态根）、版本向量、父引用、谱系引用、目录序列、交接指针等；头部相等要求所有规范编码字段完全一致。
- 抽象内核配置：`C = ⟨X, B, Γ, S, t⟩`，其中 `Γ` 是前状态权威上下文，`S` 是持久元数据存储，`t` 是可信事务时间。

### 2.3 提案与类型化转移
- 提案签名摘要：`τ = ⟨pid, target, expected, ops, a, req⟩`，包含提议者唯一 ID、目标分支、期望前驱头、操作序列、权威变更序列、所需证据声明。
- 候选推导发生在提交外：`X' = F(X, ops, W)`。
- **关键防自授权设计**：授权在**前状态** `A` 上运行（`A = Γ` 或创建时的 `ξk`），先运行 `Authorize A(τ, W)`，再计算权威更新 `Γ' = FA(A, a)`；提案不能为其自身注入所需权限。
- 模式演进通过显式 `Migration` 转移并固定确定性迁移器；删除创建类型化墓碑，物理擦除受保留策略约束。

### 2.4 激活协议
- 激活事务内按固定顺序评估 **17 阶段**（ActCheck），每阶段一个谓词；只有所有阶段全 `Pass` 才接受。
- 检查内容包括：目标查找、分配、期望头（精确匹配或类型化缺失）、生命周期、交接修订、获取认证、需求覆盖、版本绑定、见证绑定、候选绑定、效果绑定、初始/最终新鲜度、授权、决策、权威转移、良好形成性。
- 处置结果为四种稳定且终局的状态：
  - `Commit`：原子安装完整接受单元（状态、权威、谱系、效果、结果、收据）；
  - `Reject`：永久验证/策略失败，不保留后继；
  - `Quarantine`：隔离密封材料，不接入权威头；
  - `Defer`：可信获取报告所需证据不可用。
- 收据分为四个递增证据级别：`Structural`（结构签名）、`Attested`（可信内核证明到达阶段）、`Replay`（用保留输入重放）、`Inclusion`（持久化包含证明）。区分“签名”与“持久包含”。

### 2.5 生命周期操作
- **分支创建**（BranchCreate）：基于类型化缺失 + 创建上下文 `ξk`，授权使用 `ξk` 而非不存在的前驱；通过原子唯一插入防止双创建者。
- **写者交接**（Handoff）：使用目录序列化的小状态机：`Prepare → Fence → Retarget → Activate`，或者 `Prepare → Abort`。先围栏源写者（去除写权限），再激活目标写者，避免裂脑双写者。
- **迁移**：显式迁移器，允许回滚为“前向迁移”，绝不改写已接受头。
- **前向恢复**：`X' = Restore_M(Xc, Mμ(Xk))`，受保护路径（权威、策略、撤销、写者、epoch、生命周期等）保持当前值，恢复不能复活旧写者或凭据。

### 2.6 安全性声明
- 在显式假设 A1–A9（边界与密码学、原子序列化、完整上下文与时间、生命周期顺序、非回收作用域、验证对象等）下，证明三个主要性质：
  1. 所有者绑定稳定结果（一个提案 ID 最多一个持久处置）；
  2. 单一精确延续（一个完整前驱最多一个接受后继）；
  3. 每个效果标识符最多一次接受绑定（包括在线记录被回收后）。

1. **存储保留 ≠ 权威**：对象是否权威只取决于它是否从当前分支头可达，而不是是否被存储。

## 9. 延伸讨论与个人思考

### 9.1 从“检索增强”到“激活治理”的范式转变

传统代理记忆研究几乎全部集中在召回质量上：更好的 embedding、重排序、压缩器、混合检索。但本文的视角完全不同——它认为在实际运行中，真正致命的问题不是“找不到相关内容”，而是“找到了多个版本但不知道哪个是生效的权威版本”。这实际上重构了问题空间：记忆系统首先是一个**状态管理基础设施**，其次才是语义检索工具。

### 9.2 设计哲学：短事务、确定性控制面

CK 强调“把非确定性留在事务外，把确定性留在事务内”。这与数据库社区关于长事务分解的理念一致。所有候选生成、网络调用、摘要压缩等耗时且可能失败的工作都在事务外完成；事务内只做 17 个确定性谓词检查，然后原子推进头部。这种设计思路值得借鉴，但其代价是：**如果候选生成与真实世界状态存在依赖，提交时可能因证据过期而拒绝**，即 Defer 处置。系统需要额外的重试与外交互机制，而这个机制本文没有展开。

### 9.3 需要警惕“权威连续性”不等同于“语义正确性”

CK 保证的是状态的**线性权威谱系**，但不保证状态内容在语义上正确。也就是说，一个“连续”的代理可能在其权威分支上逐步积累了事实上错误的记忆或策略。CK 提供的只是治理外壳，内容质量仍需依赖模型本身的推理、验证与反馈机制。明确这一点可以避免过度推销 CK。

### 9.4 现实落地的主要障碍

- 将 17 阶段谓词映射到单条数据库事务中，需要为每个谓词准备高效索引，尤其是目标查找与新鲜度检查；
- 分支目录本身可能成为热点，需要支持并发分支创建的高吞吐唯一插入；
- 收据的包含性证明如需持久化，可能需要额外的哈希链或 Merkle 化存储，带来额外写放大；
- 写者围栏在跨进程、跨网络环境下需要分布式锁或租约配合，单纯依赖本地事务不够。

### 9.5 与外部效应原子性之间的距离

作者明确承认 CK 不解决外部副作用原子性。但从代理系统实际需求来看，外部 API 调用（发送邮件、下单、修改数据库）往往比内部状态更新更关键。缺少 outbox/排空机制的设计细节，使得 CK 单独使用时的实用价值受限。未来若能与 transactional outbox、saga 模式结合，会更有落地前景。

## 10. 结语

这是一篇偏系统与基础设施的论文，视角独特，论证严谨，最突出的贡献在于将“代理记忆的权威性”从检索问题中剥离出来，提升为独立的激活契约问题。虽然缺少真实实现与性能对比，但其形式化有界验证与清晰的安全属性声明使其具有较高的可信度。对于构建长期运行、可审计、可恢复的 AI 代理系统，CK 提供了极具参考价值的设计蓝图。
