## 摘要
多智能体LLM系统常常失败，并非因为缺乏候选答案，而是因为没有持久机制来决定当前应信任哪个不兼容的主张。多数投票、辩论和基于评判的选择会选择一个输出，但不记录哪个主张获胜、哪个存在争议，或为何后来的更新会取代它。我们提出\term{LatticeMind}，一种在写入时处理矛盾的冲突感知结构化内存。它维护明确的条目状态，应用廉价的符号冲突检查，并仅在未解决的语义情况下调用LLM调解。在去除源名称提示的标签盲ConflictBank评估中，LatticeMind达到0.97的准确率，而最强聚合基线为0.61，通过配对McNemar检验，差异在$p<10^{-6}$水平显著。消融实验表明，移除检查器或调解器会损失12到14个点。在四个次要规划基准上，情况不一：LatticeMind在四个中的三个上胜过朴素合并，但在奖励迭代搜索的任务上并不能取代深思熟虑的方法。

## Abstract
Multi-agent LLM systems often fail not for lack of candidate answers, but because they have no persistent mechanism for deciding which incompatible claim should currently be trusted. Majority vote, debate, and judge-based selection choose an output without recording which claim wins, which is contested, or why a later update supersedes it. We present \term{LatticeMind}, a conflict-aware structured memory that handles contradiction at write time. It maintains explicit item status, applies cheap symbolic conflict checks, and invokes LLM reconciliation only for unresolved semantic cases. On a label-blind ConflictBank evaluation that removes source-name hints, LatticeMind reaches 0.97 accuracy versus 0.61 for the strongest aggregation baseline, with the gap significant at $p<10^{-6}$ by paired McNemar test. Ablations show that removing the checker or the reconciler costs 12 to 14 points. On four secondary planning benchmarks the picture is mixed: LatticeMind beats naive merge on three of four, but does not replace deliberation methods on tasks rewarding iterative search.

### 2. 方法论：核心思想、关键技术细节与算法流程

#### 2.1 核心设计：冲突感知内存原语

- 将每个内存条目建模为五元组：**m = (k, c, ρ, τ, η)**
  - k：键/路由句柄；
  - c：内容；
  - ρ：证据元数据；
  - τ：时间戳；
  - η：显式状态，取值 {**PROPOSED**（提出）、**CONFIRMED**（确认）、**CONTESTED**（争议）、**SUPERSEDED**（取代）}。
- 状态机约束：条目从 PROPOSED 开始；符号检查器可将其置为 CONTESTED；协调器可将其转为 CONFIRMED 或 SUPERSEDED；SUPERSEDED 为终态，禁止回退。

#### 2.2 三层处理管道（Algorithm 1）

1. **结构化写**：
  - 智能体产出 FACT、CONSTRAINT、SUB_PLAN 等结构化发现，而不是立即压平成最终答案；
  - 软件状态场景中进一步提取规范状态声明 **z = (u, σ, v, β, ε, ρ, τ)**，其中 u 为实体、σ 为槽、v 为槽值、β 为分支范围、ε 为环境、ρ 为证据、τ 为时间戳；
  - 规范键定义为 **k(z) = (u, σ, β, ε)**，使内存可以按"单个范围内的单个槽"路由，而不是把整个历史当作无差别文本。

2. **符号检查器（Symbolic Checker）**：
  - 依赖环检测：基于 DEPENDENCY 边构图，用 NetworkX 强连通分量扫描拒绝任何环；
  - 资源冲突检测：用正则 `resource:(\S+)\s+time:(\d+)-(\d+)` 解析约束，检测同一资源上 `s1 < e2 且 s2 < e1` 的时间区间重叠；
  - 只处理机械性冲突，成本可忽略。

3. **语义协调器（Semantic Reconciler）**：
  - 仅在符号检查无法裁决的语义冲突上调用 LLM，按需触发：
    - **可信度冲突（Credibility）**：一方应击败另一方 → 证据加权取代；
    - **协调冲突（Coordination）**：多个局部有效提案碰撞共享资源 → 保守安全覆写，保留双方并重跑规划（论文明确声明此分支仅为设计级安全机制，未被实证验证）。
  - 软件状态场景中，评分函数为 **s(z) = w(证据类型) + 40·1[git_commit ≠ ∅]**，证据权重从 60（code-change / incident-hotfix）递减到 4（stale-observation），Git 提交加成 40 分足以让新提交自动压过陈旧笔记。实力相当时按时效性裁决，仍打平才回退到 LLM 法官。

#### 2.3 四种更新策略

- **可信度协调**：不兼容声明描述同一事实 → 强者确认，弱者保留为 SUPERSEDED/CONTESTED；
- **协调处理**：依赖环或资源重叠 → 保留条目 + 附加冲突信号 + 重跑规划；
- **槽优先状态合并**：同一 (entity, slot, branch, env) 键、值不同 → 胜者成为当前状态，败者标记争议；
- **证据累积**：同一键和归一化值重现 → 合并来源/时间戳/证据，不产生重复条目。

#### 2.4 渲染视图与学习算子

- 渲染出的内存视图包含三部分：当前可信状态、争议条目、转换日志，下游读者只看到渲染文档；
- 另有基于 QLoRA 的三个学习算子（extract-state、compare-claims、update-memory），仅用于仓库回放研究，不参与主实验。

### 3. 实验设计

#### 3.1 主基准：ConflictBank（公开矛盾基准）

- **标签盲协议（label-blind）**：将三个证据源重命名为中性标识 Source A/B/C，移除"权威来源/替代来源/近期报告"这类可作为捷径的信任提示。
- **规模**：75 个样本；评估模型为 Qwen3-Max（OpenRouter）。
- **对比方法**（全部消费相同证据池）：
  - Single-Agent：一次读入全部证据；
  - No-Merge：多智能体输出朴素拼接；
  - Majority Vote / Debate / Judge：答案级聚合。

#### 3.2 次级公开基准（用于划定方法边界）

- NaturalPlan Calendar（n=15，精确匹配）；
- PlanBench（n=15，目标达成率）；
- TravelPlanner（n=10，约束通过率）；
- REALM JSSP（n=10，有效性率）。

#### 3.3 应用研究：软件状态追踪

- **场景族**：authority-overwrite、scope-divergence、incident-timeline；
- **最严苛测试**：BUDGETED LONG-NOISE——写入与读取都有预算约束（1700 / 1400 字符），混入陈旧、分支与文档噪声；
- **对比方法**：Concat（拼接）、LLM-Merge（一次摘要）、LLM-Merge-Inc（增量摘要）、StateMemory（LatticeMind 实例化）；
- **评测维度**：当前状态、范围感知、溯源、时序、陈旧抑制（检索答案用确定性 token 检查打分）。
- **真实仓库桥接**：基于两个真实 Codex 提交轨迹（权限流回滚、exec/app-server 回滚）的策划回放。
- **学习算子研究**：五折留一（leave-one-out）跨仓库轨迹评测，检验规则的可迁移性。

### 6. 主要结论与发现

- **主基准核心结果**：标签盲 ConflictBank 上 LatticeMind 达 0.97，远超最佳答案级基线 Majority Vote 的 0.61 和单智能体的 0.63，所有差距在 McNemar 检验下 p < 10⁻⁶。
- **消融结论**：移除符号检查器损失 12 分、移除协调器损失 14 分，两者形成互补作用；协调器消融显著（p<0.05），检查器消融方向一致但仅边缘显著。
- **边界划定**：LatticeMind 在 NaturalPlan Calendar（+13）、PlanBench（+13）、REALM JSSP（探索性 +10）上胜过朴素合并，但在 TravelPlanner 上 -7——单一约束规划任务单智能体已达 0.97，多智能体开销只会引入噪声；在奖励迭代搜索的规划任务上，辩论/法官类审议方法仍更优。
- **软件状态应用**：BUDGETED LONG-NOISE 上 StateMemory 达 0.83，显著优于最强摘要基线 LLM-Merge-Inc 的 0.70；增益集中于溯源（0.81 vs 0.61）和时序（0.77 vs 0.38）——自由文本摘要恰恰会压缩掉这两类信息。
- **学习算子/可迁移性**：冲突裁决策略（compare-claims、update-memory）在留一仓库上近乎饱和（1.00），但提取算子（extract-state）平均仅 0.30、最差为 0，约束式两阶段提取可将总体从 0.81 提到 0.86——剩余瓶颈在提取而非冲突裁决。

### 7. 优点

- **问题定位精准**：将"矛盾裁决"从答案选择问题重新定义为结构化内存更新问题，提出了此前内存架构中缺失的一等公民原语。
- **成本意识强**：符号检查 + 选择性 LLM 协调的混合管道，协调器平均每例仅调用 1.29 次，避免为每则冲突都付出大模型开销。
- **标签盲协议设计**：主动移除来源名称这一捷径线索，并量化验证了协议影响（基线降 8–15 点而 LatticeMind 仅降 2 点），显著提高了结论可信度。
- **统计规范**：McNemar 检验、bootstrap 区间、逐样本记录、不对称争议对计数（如 No-Merge 49/0）等多重证据互相印证，而非只报点估计。
- **边界意识明确**：不声称取代所有范式，主动划清"记忆更新能力强≠规划搜索强"的边界；额外加入协调处理的安全覆写机制（虽未实证但设计保守）。
- **迁移验证完整**：从合成基准到真实 Codex 轨迹回放再到学习算子留一研究，多层级证据链支撑"冲突抽象可迁移，提取是瓶颈"的结论。

- **渲染视图策略未做系统评估**：内存视图仅以渲染后的文档呈现给下游，但争议条目的排序、证据展示方式等呈现策略未单独消融，下游读者是否真正有效利用了争议信息也未直接测量。
- **智能体数量敏感性缺失**：所有实验均使用固定数量的智能体或固定证据池，未检验智能体数量增多时写路径压力增大、冲突率上升对系统吞吐与协调器调用次数的影响，工程可扩展性数据不足。
- **提取瓶颈可能是乐观估计**：学习算子研究中 extract-state 平均 0.30、最差为 0，且场景集中在日历/行程类；真实长期项目中自动提取规范状态声明的难度远高于实验室设定，该数字在真实负载下很可能进一步下降。

---

### 9. 总体评价

这篇论文的价值在于将一个零散存在于长期软件工程、多智能体协作中的工程痛点——"互斥主张反复争辩却无沉淀"——提炼为统一的形式化内存原语，并给出可工程实现的混合管道、可迁移的算子设计与可复现的评估协议。它在方法论上是克制的：符号检查器只处理低成本的机械冲突，LLM 协调器按需触发（平均每例 1.29 次），既保留了效率又保证了裁决质量；它在结论上也是克制的：明确区分"记忆更新能力强"与"规划搜索能力强"，不宣称取代审议式方法，并主动将未验证的协调分支标注为设计级安全机制。主要短板在于实验规模偏小、模型覆盖单一、真实仓库验证为策划回放，这些限制使得"冲突裁决可抽象为新内存原语"这一核心主张获得了初步且方向一致的证据，但距离大规模生产环境中的稳健性证明仍有距离。总体而言，论文贡献了一个原创性强、动机明确、可扩展的研究框架，为后续多智能体记忆系统的冲突处理研究提供了清晰的起点。
