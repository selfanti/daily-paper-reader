## 摘要
基于LLM的代理框架现已成为处理多步任务的个人助理。诸如OpenClaw之类的现有代理框架通常遵循云代理部署模式，使用闭源云LLM作为骨干模型，这可能暴露用户隐私信息并产生重复的LLM调用成本。本地代理通过在用户控制的设备上部署前沿开源SLM来解决这些部署问题，但其任务有效性仍远落后于云代理。通过诊断分析，我们揭示本地代理使用前沿SLM骨干时有效性受限的主要原因在于骨干模型规模有限导致的环境知识缺失，包括环境规则和操作流程。为了以非参数化、上下文高效且无需专家编写的方式提供此类知识，我们提出了SkillSmith，一种云-本地代理协作框架，使用技能作为上下文高效的知识载体，从云代理任务探索中自动构建技能，并利用本地代理执行反馈进化技能，以增强冻结的本地代理。在日常生活代理数据集AppWorld和WorkBench上的实验表明，自动生成的技能使带有Qwen3.6-27B（SLM）的本地代理达到与使用前沿LLM的云代理相当的任务有效性，超越最强的非参数基线，在AppWorld-Normal上将每任务平均动作数从36.1减少到9.9，并可推广到其他SLM骨干模型而无需重新运行技能构建。

## Abstract
LLM-based agent frameworks now act as personal assistants for multi-step tasks. Existing agent frameworks such as OpenClaw commonly follow the Cloud Agent depolyment mode using closed-source cloud LLMs as backbone model, which may expose private user information and incur repeated LLM-calling costs. Local Agents address these deployment concerns by depolying frontier open-source SLMs on user-controlled devices, but their task effectiveness still lags far behind Cloud Agents. Through diagnostic analysis, we reveal that the limited effectiveness of Local Agents with frontier SLM backbones mainly comes from missing environment knowledge caused by limited backbone model scale including environment rules and operation procedures. To supply such knowledge non-parametrically, context-efficiently, and without expert authoring, we present SkillSmith, a Cloud--Local Agent collaboration framework that uses Skill as a context-efficient knowledge carrier, automatic constructs Skill from Cloud Agent task exploration and evolves Skill using Local Agent execution feedback to enhance a frozen Local Agent. Experiments on daily agent task datasets AppWorld and WorkBench show that the automatically generated Skill enables the Local Agent with Qwen3.6-27B(SLM) to achieve task effectiveness comparable to Cloud Agents with frontier LLMs, outperform the strongest non-parametric baselines, reduce average actions per task from 36.1 to 9.9 on AppWorld-Normal, and generalize to other SLM backbone models without rerunning Skill construction.

## 1. 核心问题与整体含义（研究动机与背景）

当前基于LLM的代理框架（如OpenClaw、Claude Code、Hermes）已成为执行多步任务的个人助理，但主流部署模式是**云代理（Cloud Agent）**，即使用闭源云端LLM作为骨干模型。这种模式存在两个严重问题：

- **隐私泄露风险**：每次执行步骤都需要将本地任务上下文（可能包含用户文件、账户信息等）发送到云端LLM；
- **成本高昂**：每次执行步骤都调用云端付费API，产生重复且持续递增的LLM调用成本。

为了应对上述问题，研究者提出**本地代理（Local Agent）**模式，即在用户控制的本地设备上部署开源小语言模型（SLM，参数通常低于35B）。然而，本地代理的实际任务效果远逊于云代理：例如在AppWorld-Normal上任务通过率仅为36.3%，而Claude Opus 4.7达到94.0%。

论文通过诊断分析揭示了一个关键认识：**本地代理性能差距的主要来源既不是模型推理能力不足，也不是工具调用能力缺陷，而是"环境知识"缺失**——包括目标应用环境中的规则（environment rules）和操作流程（operation procedures）。具体而言，论文有三项实证发现：

1. **核心代理能力已基本对齐**：Qwen3.6-27B（SLM）在SWE-bench Verified、Terminal-Bench、QwenClawBench、GPQA Diamond等基准上已与Claude Opus 4.5相当（差距在±3.7个百分点以内），说明模型规模并不决定核心代理能力。
2. **失败主要由环境知识缺失导致**：对36条失败轨迹的归因分析显示，91.7%的失败源于缺少环境规则（52.8%）或操作流程（38.9%）。
3. **非参数化补充环境知识有效**：手工编写的环境知识注入提示词后，可以在不微调模型的情况下解决33个知识相关失败中的26个（78.8%）。

因此，论文的核心主张是：**通过非参数方式（而非微调模型参数）为冻结的本地SLM补充环境知识，就能大幅提升任务有效性**。这一思路需要在满足三个需求的前提下落地：(R1) 上下文高效的合适知识载体；(R2) 无需专家编写的高质量初始知识自动构建；(R3) 基于本地代理执行反馈的自动迭代进化与验证修正。SkillSmith正是为此设计。

## 2. 论文提出的方法论

### 2.1 核心思想

SkillSmith的核心思想是**云-本地双代理协作**：

- **离线学习阶段**：利用云端大模型（Cloud Agent）的丰富参数化环境知识和更强的反思归纳能力，从代表性任务执行中自动构建初始Skill；然后利用本地小模型（Local Agent）执行当前Skill产生的失败反馈，驱动云端大模型迭代进化Skill。
- **在线服务阶段**：将最终Skill部署到冻结的本地SLM上，**全程无云API调用，所有用户数据留在本地**。

其中"Skill"采用Anthropic Agent Skills的定义：S = (M, R, C)，其中M是主说明文件（SKILL.md），R是引用文件集合（存环境规则与操作流程），C是每个引用的加载条件。技能支持**渐进式披露（progressive disclosure）**：执行时只加载与当前任务相关的知识而非全部知识集合，从而实现上下文高效。

### 2.2 问题形式化

SkillSmith将离线技能学习建模为**黑盒优化**问题。目标是找到一个满足长度预算Lmax的Skill，最大化冻结本地代理的期望通过率：

S* = argmax S∈SLmax Eξ∼T [r(S; ξ)]

实际中采用训练集的经验通过率作为目标函数，但由于SLmax是离散自然语言文档空间且目标无梯度，SkillSmith**类比TextGrad**，将云端Agent Gc作为文本优化器，先后执行两个算子：

- S0 = Create(Gc, Dtrain)（技能创建）
- Si = Evolve(Gc, Gs, Si−1, Dtrain)，i = 1,...,R（技能进化）

### 2.3 技能创建阶段（Skill Creation）

**第1步：探索与反思（Explore and Reflect）**。云代理逐个执行训练任务，获取评估器反馈后撰写反思报告（Reflection Report）。报告包含：任务描述、压缩执行轨迹、评估结果、更高效率的解决方案路径、遇到的陷阱、使用到的工具。避免使用原始轨迹（含冗余观察、探索绕路和失败尝试）。

**第2步：创建初始技能（Create Initial Skill）**。引入三个云代理角色：

- **Cluster Agent（聚类代理）**：将反思报告按任务类型/应用/工具分组聚类，合并小簇，控制总簇数≤10；
- **Distill SubAgent（提炼子代理）**：每个簇分配一个子代理，提取复用信号生成insight文件，包括：步骤序列及代码模板（附频率）、陷阱及触发条件与补救方法（附频率）、簇特定规则、任务文本触发关键词、跨簇通用性判断；
- **Merge Agent（合并代理）**：将各簇insight合并为初始Skill——跨簇高频规则提升到SKILL.md主文档，场景特定细节写入reference文件并配对应加载触发条件，受Lmax约束。

### 2.4 技能进化阶段（Skill Evolution）

**第1步：执行与压缩（Execute and Compress）**。使用当前Skill Si−1让本地代理执行训练任务，将失败执行轨迹结合评估器反馈和Skill加载记录压缩为失败报告（Failure Report），内容包含任务、执行轨迹、评估得分和失败断言。

**第2步：进化技能（Evolve Skill）**。同样引入三个云代理角色：

- **Cluster Agent**：按任务类型和失败断因聚类失败报告（簇数≤10）；
- **Analyze SubAgent（分析子代理）**：每个失败簇分配一个子代理，对照当前Skill进行**失败归因（failure attribution）**，分为四类：
  - A类：Skill或reference未被正确加载（修改触发条件）；
  - B类：Skill指令不完整或错误（增加修改评论）；
  - C类：粗心错误/接近成功（添加快速检查项）；
  - 非Skill可解决原因（不修改）。
  同时根据失败频率给出修改优先级；
- **Merge Agent**：合并所有修改笔记，解决冲突，按优先级施加有界编辑，超过长度预算时执行压缩操作。

进化循环进行R轮（实验中为5轮），最终选取训练集经验通过率最高的Skill版本作为部署版本。

### 2.5 算法流程（Algorithm 1）

```
输入：训练任务Dtrain，云代理Gc，本地代理Gs，进化轮数R，容量Lmax
Part I 技能创建：
  1. Q ← EXECUTEREFLECT(Gc, Dtrain)      # 云代理执行并反思
  2. {Qc} ← CLUSTER(Gc, Q)               # 聚类
  3. Ic ← DISTILL(Gc, Qc)                # 并行提炼
  4. S0 ← MERGE(Gc, {Ic}, Lmax)          # 合并为初始技能
Part II 技能进化：
  5. 用S0执行本地代理，生成失败报告B−1和初始通过率
  6. for i = 1 to R:
       - 聚类失败报告 → 并行分析写修改笔记 → 合并更新为Si
       - 用Si重新执行，得到新通过率ji
       - 如果ji > j*，更新最优Skill版本
  7. 返回最优Skill S*
```

- **Trace2Skill**：基于执行轨迹自动修订已有技能（初始化技能由数据集描述生成）。

### 3.3 实现细节

- 云端模型：Claude Code SDK + Claude Opus 4.7；
- 本地代理：Hermes代理框架 + Qwen3.6-27B；
- Skill长度预算：主手册不超过400行，每个reference文件不超过250行；
- 进化轮数：5轮；
- 公平性保障：所有非云端方法均使用相同的Hermes框架和Qwen3.6-27B骨干。

### 3.4 评估指标

- **PR（Pass Rate）**：任务通过率（两个数据集均使用）；
- **AS（Average evaluator Score）**：AppWorld的评估器平均得分；
- 动作数（每任务平均动作次数）、累计上下文/输出token数（衡量开销）。

## 4. 资源与算力

**论文没有明确给出GPU型号、数量或训练时长**。由于SkillSmith的核心是**免微调**的非参数增强方法，离线阶段仅涉及云LLM（Claude Opus 4.7）的API调用和本地SLM（Qwen3.6-27B）的推理执行，**不存在模型训练的GPU算力消耗**。

论文给出了可量化的**API成本**数据：
- AppWorld上生成可部署Skill的总离线成本为 **$87.95**（其中技能进化占$52.40）；
- WorkBench上总成本为 **$77.27**（技能进化占$53.89）；
- 作为对比，云代理的API成本随时间递增：**约560个AppWorld任务或约1,400个WorkBench任务后**，云代理的累计调用成本已超过SkillSmith的一次性构建成本，而SkillSmith部署后持续免费服务。

补充：在线推理开销量化——AppWorld上加载Skill后每任务平均动作数从36.1降至9.9，累计上下文tokens从450.7k降至200.6k；WorkBench上动作数从8.0降至6.5，但累计上下文从32.6k增至99.8k（因需读取技能内容）。

## 5. 实验数量与充分性

### 5.1 实验组数概览

1. **主实验（RQ1）**：在3个任务集（AppWorld-Normal、AppWorld-Challenge、WorkBench）上对比8种方法（2个云LLM、1个vanilla SLM、2个提示词方法、2个记忆方法、1个技能方法 + SkillSmith），记录PR和AS指标。这是对任务有效性的全面横向对比。
2. **成本分析（RQ2）**：离线API成本按阶段分解，在线推理开销（动作数、上下文tokens、输出tokens）对比。
3. **消融实验（RQ3）**：
   - 阶段级消融：No Skill vs. Skill Creation only vs. Creation + Evolution（3个数据集）；

- 训练任务集规模有限（180/207个），大规模数据下的表现未知；
- WorkBench上每类方法只报告PR，未报告AS（该数据集可能无此指标）；
- 消融实验未单独分离聚类、提炼、合并各子模块的贡献；
- 进化轮数固定为5，未报告不同轮数的影响或收敛性分析（虽然有跨版本的演化轨迹图）。

## 6. 主要结论与发现

1. **本地代理性能瓶颈主要是环境知识而非核心能力**。91.7%的失败归因于环境规则或操作流程缺失，而这些缺失可通过非参数注入得到大部分修复。

2. **SkillSmith显著超越所有非参数基线**：在AppWorld-Normal达到78.6% PR（最强基线ExpeL为65.9%，领先12.7个百分点）；在AppWorld-Challenge达到74.9%（最强基线ExpeL为62.1%，领先12.8个百分点）；在WorkBench达到89.0%（最强基线Trace2Skill为62.8%，**领先26.2个百分点**）。

3. **本地代理接近甚至超越云代理效果**：
   - AppWorld-Normal：本地+SkillSmith（78.6%）与Claude Opus 4.7（94.0%）差距从57.7点缩小到15.4点；
   - AppWorld-Challenge：差距从61.1点缩小至14.3点；
   - WorkBench：本地+SkillSmith（89.0%）**反超**最强云代理GPT-5.5（75.4%），领先13.6点。

4. **技能创建是主导贡献、进化提供增量优化**：
   - 创建阶段增益：AppWorld-Normal +30.0点、Challenge +43.5点、WorkBench +36.7点；
   - 进化阶段增益：分别+12.3、+3.3、+1.2点。初始技能质量越高，进化剩余空间越小。

5. **在线推理效率大幅提升**：AppWorld-Normal上每任务平均动作数从36.1降至9.9（减少72.6%），累计上下文tokens从450.7k降至200.6k，输出tokens从6.3k降至3.7k。

6. **技能具有跨骨干模型泛化性**：无需重新构建，同一Skill在Qwen3.6-30B-A3B上提升20.1~30.8点、在Gemma-4-31B上提升7.8~48.2点（增值因数据集而异）。
