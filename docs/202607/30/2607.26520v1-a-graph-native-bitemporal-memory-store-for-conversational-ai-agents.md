## 摘要
对话式AI代理通常缺乏跨会话的持久记忆。显而易见的修复方法，比如将完整聊天历史注入上下文窗口，或委托给第三方记忆服务，要么耗尽模型的上下文预算，要么通过用户无法控制的基础设施发送个人数据。我们描述了一种避免这两个问题的记忆存储：一个代理本地的Neo4j属性图，辅以HNSW向量索引和完整的双时态数据模型。每个记忆存储为一个不可变的身份节点，链接到带有两个左闭右开时间区间的版本化内容节点：有效时间（事实在现实世界中为真的时间）和事务时间（数据库记录它的时间）。这种设计支持时间点语义检索，无需物理覆盖历史。相关记忆之间的语义边在写入时自动维护，使用1024维嵌入的余弦相似度。我们在LongMemEval上评估该系统，这是一个涵盖六种问题类型的500个问题基准测试，旨在测试长期记忆。在60个抽样问题中，当前状态语义搜索路径总体达到46.7%的R@10，在知识更新问题上提高到80%。时间旅行路径在知识更新问题上产生80%的R@10，但在时间推理问题上召回率下降（从50%降至37.5%），这是后过滤稀释的结果，直接指向具体的设计改进。我们讨论了这些结果揭示了纯检索对不同问题类型的局限性，以及每种失败模式对未来工作的启示。

## Abstract
Conversational AI agents commonly lack persistent memory across sessions. The obvious fixes like injecting full chat histories into the context window, or delegating to a third-party memory service, either exhaust the model's context budget or send personal data through infrastructure the user does not control. We describe a memory store that avoids both problems: an agent-local Neo4j property graph augmented with HNSW vector indexes and a full bitemporal data model. Each memory is stored as an immutable identity node linked to versioned content nodes carrying two closed-open time intervals: valid time (when the fact was true in the world) and transaction time (when the database recorded it). This design supports point-in-time semantic retrieval without physically overwriting history. Semantic edges between related memories are maintained automatically at write time using cosine similarity over 1024-dimensional embeddings. We evaluate the system on LongMemEval, a 500-question benchmark spanning six question types designed to stress long-term memory. Across 60 sampled questions, the current-state semantic search path achieves 46.7% R@10 overall, rising to 80% on knowledge-update questions. The time-travel path yields 80% R@10 on knowledge-update but decreases recall on temporal-reasoning questions (50% to 37.5%), a consequence of post-filter dilution that points directly to a concrete design improvement. We discuss what these results reveal about the limits of pure retrieval for different question types and what each failure mode suggests for future work.

## 2. 方法论
### 核心思想
- 采用**图原生（Graph-Native）架构**：基于Neo4j属性图，结合HNSW向量索引和双时态数据模型。
- 记忆存储为**不可变的身份节点**（`:Memory`）与**版本化内容节点**（`:MemoryVersion`）分离，历史版本永不物理覆盖。
- 每一条记忆携带两个时间区间：**有效时间（valid_time）**（事实在现实世界为真的时间）和**事务时间（transaction_time）**（数据库记录该事实的时间），均为左闭右开区间。
- 语义相似记忆之间自动维护`RELATED_TO`边，基于1024维嵌入的余弦相似度（阈值≥0.75）在写入时动态创建。

### 关键技术细节
- **数据模型**：
  - `:Memory{id}`：持久身份节点，永不更新或删除。
  - `:MemoryVersion{...}`：存储实际内容、嵌入、类别、标签及四个时间戳。当前版本额外标记`:CurrentVersion`标签。
  - 关系类型：`HAS_VERSION`（连接身份节点与版本节点）、`RELATED_TO`（语义相似关系）。
- **双时态操作**：
  - 更新记忆时：关闭当前版本的`tx_to`（设为当前时间）并移除`:CurrentVersion`标签，创建新版本。
  - 删除记忆时：同时关闭`tx_to`和`valid_to`，不物理删除。
- **双索引检索设计**：
  - 当前状态检索：仅索引`:CurrentVersion`标签的节点，快速返回最新版本。
  - 历史检索：索引所有`:MemoryVersion`，先过取10×k个候选，再按有效时间和事务时间条件后过滤。
- **自动边构建**：每次写操作后，查询当前版本嵌入的top-5最相似记忆（余弦≥0.75），建立/更新`RELATED_TO`边。
- **回环集成**：智能体通过工具调用接口（9个工具：写操作、当前状态检索、时间感知检索、图关联获取等）与记忆存储交互。仅索引用户消息，忽略助手回复。

## 6. 主要结论与发现
- **当前状态检索**：总体R@10为46.7%。单会话用户陈述类最好（90%），知识更新类次之（80%），多会话类最差（30%，且R@1为0%）。
- **时间旅行检索**：在知识更新问题上和当前状态检索持平（80%），但在时间推理问题上召回率下降（从50%降至37.5%）。
- **失败模式分析**：
  - **ss-asst（20%）**：因只索引用户消息导致无法检索助手输出。
  - **ss-pref（10%）**：真实答案为多句摘要，不在任何用户消息中，无法精确检索。
  - **multi-session（30%）**：需要跨会话计数/聚合，纯检索无法回答。
  - **temporal-reasoning时间旅行路径下降**：因过取因子10×k导致后过滤稀释，大量不相关候选占据前十位。
- **核心启示**：纯检索对不同问题类型能力差异显著，时间旅行路径的缺陷指导了具体改进方向（如重排序时结合相似度和时间接近性）。

## 7. 优点
- **隐私友好**：本地优先设计，数据不离开用户控制域，避免第三方服务潜在泄露。
- **历史完整性**：双时态模型支持时间点语义检索且不覆盖历史，适合需要审计或回溯的应用。
- **图增强检索**：自动构建语义边提供`get_related_memories`操作，比重复向量查询更高效稳定。
- **灵活的双索引设计**：利用Neo4j标签区分当前版本和全量版本，实现低延迟当前状态检索和完整历史检索并存。
- **可操作的分析**：明确提出后过滤稀释问题及其解决方法（重排序），而非仅报告性能。

## 8. 不足与局限
- **实验规模有限**：仅60个问题，每类10个，统计显著性不足。
- **缺乏公平对比**：未与现有记忆系统（MemGPT、Mem0、Zep等）在同一基准上定量比较，无法说明性能优劣。
- **设计缺陷未修复**：时间旅行的过取策略导致召回下降，提议的重排序尚未实现。
- **助手消息缺失**：仅索引用户消息，导致助手相关类问题天然不可答（ss-asst为20%本质上是设计选择而非检索问题）。
- **不支持聚合/推理**：多会话计数、偏好推断等需要事中聚合或推理的任务，纯检索无法处理，但论文未尝试引入推理模块。
- **应用限制**：依赖于Neo4j图数据库和AWS Bedrock/Anthropic API，可能带来成本和可用性问题；大规模部署时HNSW索引与后过滤的性能开销未评估。
- **偏差风险**：样本为随机抽取（seed=42），未说明多次重复实验的稳定性；LongMemEval为合成数据，真实场景泛化性未知。
